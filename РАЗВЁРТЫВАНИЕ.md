# Развёртывание — пошаговая инструкция

Репозиторий: `https://github.com/BaukovGK/CalcKP.git`
CI/CD: `.github/workflows/ci-cd.yml`

Схема: **push в `master` → GitHub гоняет тесты → заходит на сервер по SSH →
`git fetch --all` + `git reset --hard origin/master` + `docker compose up -d --build`.**

Обратите внимание: деплой-скрипт (`.github/workflows/ci-cd.yml:96-97`) делает
именно `reset --hard`, а не `git pull`. Рабочее дерево сервера приводится к
состоянию `origin/master` — **любые правки в отслеживаемых файлах на сервере
будут затёрты без предупреждения**. Неотслеживаемых файлов это не касается,
поэтому `.env` (он в `.gitignore`) деплой переживает.

Доступ к git — **по HTTPS + токен** (проще ключей): и ваш push, и `git fetch`
на сервере. SSH остаётся ровно в одном месте — когда GitHub Actions заходит
на ваш сервер выполнить деплой (это по определению SSH к вашей машине).

> Что где нужно:
> - **Токен для push** (ваша машина → GitHub) — обычно Git подставит через браузер, вручную не требуется.
> - **Токен на сервере** (сервер → GitHub, чтобы читать приватный репозиторий) — fine-grained PAT с правом *Contents: Read*.
> - **SSH-ключ Actions → Сервер** — приватная часть в секрете `DEPLOY_SSH_KEY`, публичная — в `authorized_keys` сервера.

## Часть 1. Первая публикация в GitHub ✅ ВЫПОЛНЕНО

Код уже в репозитории (`origin` → `https://github.com/BaukovGK/CalcKP.git`,
ветка `master`). Обычный релиз впредь — просто:

```bash
git push
```

При первом push Git for Windows открывает окно **Git Credential Manager** →
«Sign in with browser» → вход в GitHub — токен вручную создавать не нужно.
Если GCM спросит логин/пароль, вместо пароля вставьте **Personal Access
Token** (GitHub → Settings → Developer settings → Tokens; fine-grained с
правом *Contents: Read and write* на `CalcKP`, либо classic со scope `repo`).

Каждый push запускает CI (вкладка **Actions**): typecheck + тесты фронта и
бэка.

> **Про деплой без настроенного сервера.** У job'а `deploy` нет условия на
> секреты — только `if: github.ref == 'refs/heads/master' && github.event_name
> == 'push'` (`ci-cd.yml:81`). Значит при первом же push в `master` он
> попытается стартовать и, если `DEPLOY_SSH_*` пусты, **упадёт** на шаге
> `appleboy/ssh-action` — запуск будет красным, а не «пропущенным». Это
> ожидаемо, пока не пройдены части 2–3.
>
> `deploy` объявлен как `needs: [frontend, backend]`, поэтому запускается
> только после зелёных проверок обеих job.

## Часть 2. Подготовить сервер (один раз)

Целевая площадка — виртмашина на **Ubuntu** (22.04/24.04 LTS). Ниже —
подготовка с нуля. Команды под root; если зашли обычным пользователем —
добавляйте `sudo`.

### Шаг 2.0. Базовая настройка чистой Ubuntu-VM

```bash
# 1. Обновить систему
apt update && apt upgrade -y

# 2. Отдельный пользователь для деплоя (не работать под root)
adduser --disabled-password --gecos "" deploy
usermod -aG sudo deploy
# скопировать в него ваш SSH-доступ (тот же ключ, которым заходите на VM):
rsync --archive --chown=deploy:deploy ~/.ssh /home/deploy/

# 3. Файрвол: только SSH, HTTP и HTTPS
apt install -y ufw
ufw allow OpenSSH        # 22 — доступ и деплой от GitHub Actions
ufw allow 80/tcp         # приложение сейчас
ufw allow 443/tcp        # HTTPS заранее — чтобы TLS потом встал без переделок
ufw --force enable

# 4. Swap (если у VM < 2 ГБ RAM — иначе сборка фронта может упасть по памяти)
fallocate -l 2G /swapfile && chmod 600 /swapfile
mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab
```

Дальнейшие шаги — под пользователем `deploy` (`su - deploy`).

### Шаг 2.1. Установить Docker и Compose

```bash
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER      # запускать docker без sudo
newgrp docker                       # применить группу в текущей сессии
docker compose version              # проверка: должна быть v2+
```

### Шаг 2.2. Токен для доступа сервера к репозиторию

Репозиторий приватный, поэтому серверу нужен токен на чтение. На GitHub:
**Settings → Developer settings → Personal access tokens → Fine-grained
tokens → Generate new token**:
- **Repository access** → Only select repositories → `CalcKP`;
- **Permissions → Repository → Contents: Read-only**;
- срок — на ваше усмотрение (можно «No expiration» для сервера).

Скопируйте токен (`github_pat_…`) — он понадобится в шаге 2.3.

### Шаг 2.3. Клонировать репозиторий (HTTPS + токен)

```bash
cd /opt                                   # или другой каталог
git clone https://<ТОКЕН>@github.com/BaukovGK/CalcKP.git
cd CalcKP
chmod 600 .git/config                     # в config попал токен — закрыть от чужих
```

Токен сохраняется в `.git/config`, поэтому последующие обращения к GitHub
(в т.ч. `git fetch --all` из деплой-скрипта) идут без запроса пароля. Полный
путь (`/opt/CalcKP`) запомните — он понадобится как секрет `DEPLOY_PATH`.

> Токен только на чтение: даже при утечке `.git/config` запись в репозиторий
> невозможна. Сменить токен позже: `git remote set-url origin https://<НОВЫЙ>@github.com/BaukovGK/CalcKP.git`.

### Шаг 2.4. Создать `.env`

Файл `.env` в git НЕ хранится (в нём пароль БД и JWT-секрет) — создаётся на
сервере и переживает все деплои.

```bash
cp .env.example .env
# сгенерировать JWT-секрет (openssl есть в Ubuntu; node на сервере нет):
openssl rand -base64 48
nano .env
```

Заполнить:
- `POSTGRES_PASSWORD` — придумать надёжный пароль;
- `JWT_SECRET` — вставить сгенерированное значение;
- `PUBLIC_URL` — внешний адрес. Сейчас (домена нет, TLS отложен):
  `http://<IP-виртмашины>`. Перед интеграцией с Битрикс24 сменить на
  `https://<домен>` (см. блок «Перед Битрикс24» ниже);
- `HTTP_PORT` — при необходимости изменить (по умолчанию 80).

### Шаг 2.5. Первый запуск вручную

```bash
docker compose up -d --build
docker compose logs -f backend        # видно миграции и сид; Ctrl+C для выхода
```

Открыть `http://<адрес-сервера>:<HTTP_PORT>` — должна открыться страница входа.

Сид заводит **одного** пользователя: `admin@ntt.local` / `admin123`, роль ADMIN
(`backend/prisma/seed.ts:80`). Без него в свежую систему было бы не войти.
Демо-учётки остальных ролей создаются только при `SEED_DEMO_USERS=1` — в
`docker-compose.yml` переменная по умолчанию `0`, на проде её не ставьте.

Порядок первого входа: зайти под `admin@ntt.local`, **сразу сменить пароль**,
затем в разделе «Администрирование» завести остальных пользователей. Свой
пароль пользователь меняет сам — `POST /api/auth/password` с подтверждением
текущего; администратор чужие пароли не меняет и не сбрасывает
(`PATCH /api/admin/users/:id` принимает только имя, роль и признак
активности), поэтому пароль новой учётки задаётся при её создании и
сообщается человеку лично.

Сид досоздаёт только недостающее (`upsert` с пустым `update`), поэтому смена
пароля и выключение учётки (`isActive` проверяется при входе и на каждом
запросе) переживают деплой.

Справочники материализации — нормы патрубков, веса труб, инженерные матрицы,
Мс — сид заливает только в пустую базу. После первого запуска их ведёт
технолог на экране «Шаблоны», и перезапуск контейнера его правок не трогает:
ни добавленные строки, ни удалённые. Если справочник разошёлся с
мастер-шаблоном, сид пишет в лог предупреждение и запуск продолжается;
строгие сверки с мастер-шаблоном идут только в CI (`SEED_STRICT=1`). Новые
справочные данные будущих релизов приходят миграцией.

## Часть 3. Включить авто-деплой (SSH-ключ Actions → сервер + секреты)

Единственное место, где нужен SSH: GitHub Actions должен зайти на ваш сервер
и выполнить `docker compose`. Дадим ему ключ.

### Шаг 3.1. Создать ключ «Actions → сервер»

Удобнее сгенерировать на своей машине (приватную часть отдадим в секрет):

```bash
ssh-keygen -t ed25519 -C "github-actions" -f ./deploy_key -N ""
```

Появятся два файла: `deploy_key` (приватный) и `deploy_key.pub` (публичный).

### Шаг 3.2. Разрешить этот ключ на сервере

Публичную часть добавить в `authorized_keys` пользователя, под которым будет
заходить workflow:

```bash
# содержимое deploy_key.pub → на сервер:
cat deploy_key.pub | ssh <user>@<сервер> "cat >> ~/.ssh/authorized_keys"
```

### Шаг 3.3. Задать секреты в репозитории

GitHub → репозиторий → **Settings → Secrets and variables → Actions →
New repository secret**. Создать:

| Секрет | Значение |
|---|---|
| `DEPLOY_SSH_HOST` | адрес сервера (IP или домен) |
| `DEPLOY_SSH_USER` | пользователь SSH (напр. `root` или `deploy`) |
| `DEPLOY_SSH_KEY` | **всё содержимое файла `deploy_key`** (приватный ключ, с строками BEGIN/END) |
| `DEPLOY_PATH` | путь к репозиторию на сервере (напр. `/opt/CalcKP`) |
| `DEPLOY_SSH_PORT` | порт SSH — только если не 22 (иначе не создавать) |

После этого удалите локальные `deploy_key` и `deploy_key.pub` — они больше
не нужны.

### Шаг 3.4. Проверить авто-деплой

Сделать любой коммит и запушить в `master`:

```bash
git commit --allow-empty -m "проверка деплоя"
git push
```

GitHub → **Actions** → открыть запуск. Порядок: «Фронт — typecheck + тесты» и
«Бэк — typecheck + миграции + сид» (параллельно) → «Деплой на сервер (SSH)».
Если все зелёные — сервер обновился.

> Если деплой понадобится сделать руками (например, секреты ещё не заведены):
> `git fetch --all && git reset --hard origin/master && docker compose up -d
> --build` в каталоге `DEPLOY_PATH`.

Проверить:

```bash
# на сервере:
docker compose ps            # контейнеры up
docker compose logs backend  # свежий старт
```

## Часть 4. Дальнейшая работа

- **Обычный релиз:** `git push` в `master` — остальное автоматически.
- **Откат:** на сервере `git reset --hard <хеш>` + `docker compose up -d --build`,
  либо revert-коммит и push.
- **Обновить `.env`:** правится на сервере вручную, деплой его не трогает;
  после правки — `docker compose up -d` (без `--build`).
- **Смотреть логи прода:** `docker compose logs -f backend` на сервере.

## Бэкап базы и откат миграции

Миграции применяются автоматически при каждом старте контейнера, и **обратного
хода у них нет**: `prisma migrate deploy` умеет только накатывать. Единственный
путь назад — восстановление из дампа. Поэтому дамп снимается сам, до миграций.

Дампы лежат в `./backups` на хосте (а не в томе Docker: том исчезнет вместе с
`docker compose down -v`, и забрать его с машины нечем). Формат — `pg_dump -Fc`,
сжатый; каждый дамп сразу после создания проверяется на читаемость, нечитаемый
удаляется — дамп, который не восстановится, хуже отсутствия дампа.

### Автоматический дамп перед миграциями

Точка входа контейнера (`backend/docker-entrypoint.sh`) перед `migrate deploy`
проверяет, есть ли неприменённые миграции, и если есть — снимает дамп с меткой
`pre-migrate`. **Не снялся дамп — миграции не применяются и контейнер не
стартует**: применить необратимое изменение к базе, для которой нет точки
возврата, хуже, чем не подняться.

| Переменная | Значение | Смысл |
|---|---|---|
| `BACKUP_BEFORE_MIGRATE` | `require` (по умолчанию) | нет дампа — нет миграций |
| | `try` | попытаться, но продолжить при неудаче |
| | `off` | не снимать (если бэкап делается снаружи) |
| `BACKUP_KEEP` | `30` | сколько последних дампов хранить |

На первом запуске (база пуста) и когда неприменённых миграций нет, дамп не
снимается — снимать нечего.

### Ручной дамп

Из админки — раздел «База данных»: список дампов, кнопки «Снять дамп», «скачать»,
«восстановить», «удалить» и загрузка файла. Каталог тот же, что у скриптов, —
дамп, снятый в браузере, виден на сервере и наоборот.

Или из командной строки:

```bash
docker compose --profile tools run --rm backup
```

> **Загруженный дамп проверяется перед применением.** `pg_restore` выполняет SQL
> из архива, а пользователь БД в образе postgres — суперпользователь, поэтому
> подсунутый файл мог бы выполнить команды в контейнере. Сервер разворачивает
> архив в SQL и отклоняет его при постороннем составе объектов или опасных
> конструкциях. Это не абсолютная защита: администратор с правом восстановления
> по существу имеет доступ к данным целиком, и ограничивать его смысла нет —
> проверка закрывает подстановку чужого файла, а не злой умысел администратора.

> **Восстановление откатывает и аудит-лог:** он хранится в этой же базе. Записи
> о действиях после снятия дампа исчезнут вместе с остальными данными; запись о
> самом восстановлении останется — она пишется после.

### Восстановление

```bash
docker compose --profile tools run --rm restore --list          # что есть
docker compose --profile tools run --rm restore --yes latest    # восстановить
```

Операция **разрушающая**: содержимое базы заменяется содержимым дампа. Без
`--yes` скрипт только предупреждает и выходит. Перед заменой он сам снимает
страховочный дамп текущего состояния с меткой `pre-restore` — если выяснится,
что восстановили не то, вернуться будет куда.

После восстановления проверьте состояние миграций:

```bash
docker compose exec backend npx prisma migrate status
```

### Откат неудачной миграции

1. `docker compose stop backend` — остановить, чтобы он не пытался мигрировать снова;
2. `docker compose --profile tools run --rm restore --list` — найти дамп с меткой
   `pre-migrate`, снятый непосредственно перед этой миграцией;
3. `docker compose --profile tools run --rm restore --yes <файл>`;
4. откатить код на предыдущий коммит (`git reset --hard <хеш>`) — иначе контейнер
   при старте применит ту же миграцию заново;
5. `docker compose up -d --build`.

### Регулярный бэкап

Дамп снимается только при миграциях и вручную — расписания в стеке нет
намеренно: планировщик на сервере надёжнее контейнера-демона и виден
администратору. Добавьте в cron пользователя `deploy`:

```cron
30 3 * * * cd /path/to/CalcKP && docker compose --profile tools run --rm backup >> /var/log/ntt-backup.log 2>&1
```

Дампы с сервера нужно **увозить**: диск сервера — не бэкап. Копируйте
`./backups` на отдельное хранилище (rsync, объектное хранилище, что принято).

## Перед интеграцией с Битрикс24 — включить HTTPS

Сейчас приложение работает по `http://<IP>`. Битрикс24 встраивает вкладку
через iframe и **требует HTTPS с валидным сертификатом** — по IP и по HTTP
вкладка не откроется. Что нужно сделать (порт 443 в файрволе уже открыт,
шаг 2.0):

1. **Домен.** Завести доменное имя (напр. `calc.компания.ру`) и направить
   его A-записью на IP виртмашины. Let's Encrypt по «голому» IP сертификат
   не выдаёт — домен обязателен.
2. **TLS-терминатор.** Простейший вариант — добавить в стек **Caddy**: он
   сам получает и продлевает сертификат Let's Encrypt. Альтернативы —
   системный nginx + certbot, либо внешний прокси (Cloudflare/корп. шлюз),
   тогда на VM остаётся HTTP:80.
3. **Переключить конфиг:** в `.env` задать `PUBLIC_URL=https://<домен>`
   (от него зависит `CORS_ORIGIN` бэкенда) и передеплоить.

Конкретную реализацию (сервис Caddy в `docker-compose.yml` или nginx+certbot)
добавим отдельным шагом, когда появится домен — это правка на 20 минут.

## Защита ветки (рекомендуется)

GitHub → **Settings → Branches → Add branch protection rule** для `master`:
включить «Require status checks to pass before merging» → выбрать
«Фронт — typecheck + тесты» и «Бэк — typecheck + миграции + сид». Тогда
сломанный код физически не попадёт в `master`, а значит и на сервер.

Имена чеков GitHub берёт из `name:` job'а, а не из его id
(`.github/workflows/ci-cd.yml:21` и `:38`), поэтому в списке видны русские
названия. Не вводите `frontend`/`backend` вручную: такого чека не существует,
контекст навсегда останется в состоянии ожидания и заблокирует мерджи.

Обе job зелёные, так что обязательными можно делать сразу оба чека.

## Диагностика

| Симптом | Причина / решение |
|---|---|
| push просит логин/пароль | вставить Personal Access Token вместо пароля (часть 1) |
| push: `403`/`Authentication failed` | у токена нет права *Contents: Read and write* на `CalcKP` |
| CI: backend падает на `migrate deploy` | расхождение `schema.prisma` и миграций — создать миграцию `npx prisma migrate dev` и запушить |
| CI: frontend падает на `check:lint` | линт в CI идёт без `--fix`: прогоните `npm run lint` локально и закоммитьте правки |
| deploy: job не запустился («skipped») | красная job в `needs: [frontend, backend]` — смотрите, какая из двух упала |
| deploy: `Permission denied` в шаге SSH | неверный `DEPLOY_SSH_KEY`/`_USER`/`_HOST` или публичный ключ не в `authorized_keys` (часть 3) |
| deploy: `git fetch` на сервере просит пароль | токен не зашит в remote сервера (часть 2, шаг 2.3) или истёк |
| правки, сделанные на сервере, пропали после деплоя | так и задумано: деплой делает `git reset --hard origin/master`; правьте код только через репозиторий |
| приложение не открывается после деплоя | `docker compose logs` на сервере; проверить `.env` и занятость `HTTP_PORT` |
| Битрикс24 не пускает во вкладку | нужен HTTPS с валидным сертификатом на `PUBLIC_URL` |
