# Развёртывание — пошаговая инструкция

Репозиторий: `git@github.com:BaukovGK/CalcKP.git`
CI/CD: `.github/workflows/ci-cd.yml`

Схема: **push в `master` → GitHub гоняет тесты → заходит на сервер по SSH →
`git pull` + `docker compose up -d --build`.**

> ⚠️ В схеме два РАЗНЫХ SSH-ключа — не перепутайте:
> - **Ключ A (Сервер → GitHub)** — чтобы сервер мог `git pull` приватный репозиторий. Это *deploy key* репозитория.
> - **Ключ B (GitHub Actions → Сервер)** — чтобы workflow мог зайти на сервер. Его приватная часть лежит в секрете `DEPLOY_SSH_KEY`, публичная — в `authorized_keys` сервера.

---

## Часть 1. Первая публикация в GitHub (с вашей рабочей машины)

### Шаг 1.1. Проверить доступ к GitHub по SSH

```bash
ssh -T git@github.com
```

- Ответ `Hi BaukovGK! You've successfully authenticated…` → переходите к шагу 1.3.
- `Permission denied (publickey)` → нужен SSH-ключ (шаг 1.2).

### Шаг 1.2. Создать SSH-ключ и добавить в GitHub (если его нет)

```bash
ssh-keygen -t ed25519 -C "ваш-email"      # Enter на все вопросы
cat ~/.ssh/id_ed25519.pub                  # скопировать вывод целиком
```

На github.com: **Settings → SSH and GPG keys → New SSH key** → вставить
публичный ключ → сохранить. Повторить `ssh -T git@github.com` — должно
поздороваться.

### Шаг 1.3. Запушить код

Remote `origin` уже настроен. Из каталога проекта:

```bash
git push -u origin master
```

Откройте репозиторий на GitHub — код на месте, во вкладке **Actions** пойдёт
первый прогон CI (тесты). Деплой на этом прогоне НЕ выполнится, пока не
настроены секреты (часть 3).

## Часть 2. Подготовить сервер (один раз)

Предполагается Ubuntu/Debian с root или sudo. Адаптируйте под свой дистрибутив.

### Шаг 2.1. Установить Docker и Compose

```bash
curl -fsSL https://get.docker.com | sh
docker compose version      # проверка: должна быть v2+
```

### Шаг 2.2. Дать серверу доступ к приватному репозиторию (Ключ A)

Сгенерировать на сервере ключ и зарегистрировать его как **deploy key**:

```bash
ssh-keygen -t ed25519 -C "calckp-server" -f ~/.ssh/id_ed25519 -N ""
cat ~/.ssh/id_ed25519.pub
```

На GitHub: репозиторий → **Settings → Deploy keys → Add deploy key** →
вставить публичный ключ, галку «Allow write access» НЕ ставить (нужно только
чтение) → сохранить.

Проверить: `ssh -T git@github.com` на сервере должно поздороваться.

### Шаг 2.3. Клонировать репозиторий

```bash
cd /opt                                   # или другой каталог
git clone git@github.com:BaukovGK/CalcKP.git
cd CalcKP
```

Полный путь (`/opt/CalcKP`) запомните — он понадобится как секрет `DEPLOY_PATH`.

### Шаг 2.4. Создать `.env`

Файл `.env` в git НЕ хранится (в нём пароль БД и JWT-секрет) — создаётся на
сервере и переживает все деплои.

```bash
cp .env.example .env
# сгенерировать JWT-секрет:
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
nano .env
```

Заполнить:
- `POSTGRES_PASSWORD` — придумать надёжный пароль;
- `JWT_SECRET` — вставить сгенерированное значение;
- `PUBLIC_URL` — внешний адрес (для Битрикс24 — домен с валидным TLS,
  напр. `https://calc.вашдомен.ру`);
- `HTTP_PORT` — при необходимости изменить (по умолчанию 80).

### Шаг 2.5. Первый запуск вручную

```bash
docker compose up -d --build
docker compose logs -f backend        # видно миграции и сид; Ctrl+C для выхода
```

Открыть `http://<адрес-сервера>:<HTTP_PORT>` — должна открыться страница входа.
Учётки создаёт сид (для локальной разработки; на проде смените пароли через
раздел «Администрирование»).

## Часть 3. Включить авто-деплой (Ключ B + секреты)

Теперь дать GitHub Actions право заходить на сервер.

### Шаг 3.1. Создать ключ «Actions → сервер»

Удобнее сгенерировать на своей машине (приватную часть отдадим в секрет):

```bash
ssh-keygen -t ed25519 -C "github-actions" -f ./deploy_key -N ""
```

Появятся два файла: `deploy_key` (приватный) и `deploy_key.pub` (публичный).

### Шаг 3.2. Разрешить этот ключ на сервере

Публичную часть добавить в `authorized_keys` пользователя, под которым будет
заходить workflow:

```bash
# содержимое deploy_key.pub → на сервер:
cat deploy_key.pub | ssh <user>@<сервер> "cat >> ~/.ssh/authorized_keys"
```

### Шаг 3.3. Задать секреты в репозитории

GitHub → репозиторий → **Settings → Secrets and variables → Actions →
New repository secret**. Создать:

| Секрет | Значение |
|---|---|
| `DEPLOY_SSH_HOST` | адрес сервера (IP или домен) |
| `DEPLOY_SSH_USER` | пользователь SSH (напр. `root` или `deploy`) |
| `DEPLOY_SSH_KEY` | **всё содержимое файла `deploy_key`** (приватный ключ, с строками BEGIN/END) |
| `DEPLOY_PATH` | путь к репозиторию на сервере (напр. `/opt/CalcKP`) |
| `DEPLOY_SSH_PORT` | порт SSH — только если не 22 (иначе не создавать) |

После этого удалите локальные `deploy_key` и `deploy_key.pub` — они больше
не нужны.

### Шаг 3.4. Проверить авто-деплой

Сделать любой коммит и запушить в `master`:

```bash
git commit --allow-empty -m "проверка деплоя"
git push
```

GitHub → **Actions** → открыть запуск. Порядок: `frontend` и `backend`
(тесты) → `deploy`. Если все зелёные — сервер обновился. Проверить:

```bash
# на сервере:
docker compose ps            # контейнеры up
docker compose logs backend  # свежий старт
```

## Часть 4. Дальнейшая работа

- **Обычный релиз:** `git push` в `master` — остальное автоматически.
- **Откат:** на сервере `git reset --hard <хеш>` + `docker compose up -d --build`,
  либо revert-коммит и push.
- **Обновить `.env`:** правится на сервере вручную, деплой его не трогает;
  после правки — `docker compose up -d` (без `--build`).
- **Смотреть логи прода:** `docker compose logs -f backend` на сервере.

---

## Защита ветки (рекомендуется)

GitHub → **Settings → Branches → Add branch protection rule** для `master`:
включить «Require status checks to pass before merging» → выбрать `frontend`
и `backend`. Тогда сломанный код физически не попадёт в `master`, а значит и
на сервер.

## Диагностика

| Симптом | Причина / решение |
|---|---|
| `Permission denied (publickey)` при push | нет вашего ключа в GitHub → часть 1, шаг 1.2 |
| CI: backend падает на `migrate deploy` | расхождение `schema.prisma` и миграций — создать миграцию `npx prisma migrate dev` и запушить |
| deploy: `Permission denied` в шаге SSH | неверный `DEPLOY_SSH_KEY`/`_USER`/`_HOST` или публичный ключ не в `authorized_keys` (часть 3) |
| deploy: `git pull` на сервере просит пароль | не настроен deploy key сервера (часть 2, шаг 2.2) |
| приложение не открывается после деплоя | `docker compose logs` на сервере; проверить `.env` и занятость `HTTP_PORT` |
| Битрикс24 не пускает во вкладку | нужен HTTPS с валидным сертификатом на `PUBLIC_URL` |
