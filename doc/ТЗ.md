# Техническое задание: НТТ Калькулятор стоимости изделий

**Версия:** 1.6 (v1.1 — дополнена по реверс-инжинирингу 6 реальных Excel-калькуляторов, см. `doc/Реверс_калькуляторов.md`; v1.2 — интеграция с Битрикс24, §10; v1.3 — компонентная модель: единый рекурсивный узел каталога, материализация, Json-дерево расчёта, реестр формул в коде, роль TECHNOLOG — см. `doc/Библиотека_компонентов.md`; v1.4 — решения дизайн-сессии: авторасчёт PN/SN и арматуры в ОЛ, дизайн-токены — см. `design_handoff_ntt_calculator/README.md`; v1.5 — реальный бизнес-процесс: согласование вынесено из системы, точка фиксации — выпуск КП; v1.6 — приведено в соответствие с кодом: дерево расчёта вместо `bundles[]`, справочники `/api/refs/*`, редактор шаблонов, печатная форма КП, модуль насосной станции)
**Стек:** Express 5 + Prisma 7 + PostgreSQL (бэкенд) · Vue 3 + Pinia + Vue Router 5 + Vite (фронтенд)

---

## 1. Назначение системы

Веб-приложение для расчёта стоимости изделий (КНС, ЕМК, КОЛ) в составе инженерных проектов. Основные рабочие процессы:

1. Создание проекта (объект, заказчик, адрес).
2. Добавление к проекту единиц оборудования с заполнением опросного листа.
3. Детальный расчёт стоимости в Калькуляторе: материализация шаблона изделия из опросного листа, тюнинг дерева расчёта (сборки → компоненты → строки) с overrides количеств и цен (§9).
4. Выпуск КП: проверка «нет строк без цены», снапшот расчёта, печатная форма (docx / pdf). Согласование КП идёт вне системы (§4.3).
5. Заявка на закупку — отчёт по закупаемым позициям расчёта (§9.6).
6. Управление прайс-листом (ADMIN / BUYER): ручная правка цен и импорт из .xlsx.
7. Ведение справочников материализации (TECHNOLOG): нормы патрубков, веса труб, инженерные матрицы.
8. Администрирование пользователей, просмотр аудит-лога (ADMIN).

## 2. Роли пользователей

| Роль | Доступ |
|---|---|
| `ADMIN` | Полный доступ: пользователи, прайс, справочники, все проекты и расчёты, удаление проекта, перевод расчёта в REJECTED |
| `MANAGER` | Все проекты и расчёты на чтение; чужие расчёты — ещё и на правку; выпуск КП. Правка чужого проекта, удаление чужого расчёта и проекта недоступны |
| `ENGINEER` | Создание/редактирование своих проектов и расчётов, опросный лист, выпуск КП |
| `TECHNOLOG` | Редактор справочников материализации (`/templates`, см. `Библиотека_компонентов.md` §6.2); домашний экран роли — «Шаблоны»; чужие проекты и администрирование недоступны |
| `BUYER` | Прайс-лист (правка цен и импорт) + Заявка на закупку (§9.6); домашний экран роли — «Прайс». Выгрузку Заявки бэкенд разрешает и по чужому расчёту, но открыть чужой расчёт BUYER не может (`GET /api/estimates/:id` → 403), поэтому экран Заявки работает у него только по своим |
| `VIEWER` | Наблюдатель: видит все проекты, расчёты, их версии и печатные формы КП; ничего не меняет (вкладка «Расчёт» в Битрикс24, §10) |

#### PriceItem
| Поле | Тип | Описание |
|---|---|---|
| id | UUID | PK |
| lookupKey | String @unique | `"category:name:unit"` — ключ для upsert при импорте. **Важно:** в реальных калькуляторах ключ прайса составной — Категория + Наименование + ЕИ (одно наименование может существовать с разными ЕИ) |
| category | String | Категория — одна из 16 реальных (см. §9.2) |
| name | String | Наименование |
| unit | String | Единица измерения. Справочник «Списки» (`seed-data/lists.json`) даёт шесть: `шт`, `м`, `кг`, `чел. ч`, `м²`, `руб/м`. В самих ценах (`seed-data/prices.json`) вместо `руб/м` встречается `ед.` — ЕИ строки «СИЗ и РМ», её же требует движок (§9.5 п. 4) |
| priceBaseRub | Float? | Цена без скидки (кол. G листа НН) |
| discountPct | Float? | Скидка, % (в текущих файлах не используется, заложить) |
| currency | String | Валюта, по умолчанию `руб` (мультивалютность заложена в НН, не активна) |
| priceRub | Float? | Итоговая цена, ₽ (кол. J листа НН — именно её тянет расчёт) |
| supplier | String? | Поставщик. В листе НН его нет — при импорте не заполняется, задаётся вручную через `PATCH /api/prices/:id` |
| comment | String? | Комментарий (кол. K листа НН) |
| updatedAt | DateTime | Автоматически |

#### Справочники материализации

Извлечены из мастер-шаблона (`backend/tools/extract-refs.ts` → `prisma/seed-data/*.json`), читаются через `/api/refs/*`, правятся ролью TECHNOLOG через `/api/templates` (§4.2).

| Модель | Ключ | Содержание |
|---|---|---|
| `PipeWeight` | `(dn, pn, sn)` | Веса GRP-труб: толщина стенки, кг/пм — 162 позиции, DN 300…3000. `pn` здесь — `PN_трубы` (автоподбор, §9.4), **не** PN опросного листа |
| `EngineeringMatrix` | `(kind, d, lengthMm)` | Матрицы листа «Для расчетов»: `SHELL` — вес и толщина корпуса = f(Dу, L); `ELLIPTIC_BOTTOM` — масса формовки эллиптических днищ = f(Dн, L). По 140 ячеек |
| `NozzleNorm` | `dn` | Нормы простого патрубка: масса формовки гильзы и фланца, болтовое соединение — 26 позиций |
| `PePipe` | `odMm` | ПЭ-100 SDR17 — 26 позиций. Ключ — наружный диаметр, а не DN: DN в листе не уникален (125 указан и для ⌀125, и для ⌀140) |
| `Pump` | `name` | Каталог насосов Vandjord VSL — 61 модель: рабочее окно по расходу, диаметр напорного патрубка, номинальная точка и артикул. Подбор — §9.7 |
| `PumpCurvePoint` | `(pumpId, idx)` | Паспортная характеристика Q–H: 559 точек у 56 моделей (выгрузка VJ Select). Кривая невозрастающая по напору; по ней и идёт подбор. У пяти DN50/DN65 кривой нет |

## 4. Бэкенд

**Точка входа:** `backend/src/app.ts` · Порт: `3000` (env `PORT`) · Проба доступности: `GET /api/health`

### 4.1 Middleware

| Middleware | Описание |
|---|---|
| `requireAuth` | Проверяет Bearer JWT. Кладёт `userId`, `userRole` в `req`. Возвращает 401 при невалидном токене. |
| `requireRole(...roles)` | Проверяет роль после `requireAuth`. Возвращает 403. |
| `validate(zodSchema)` | Валидирует `req.body` через Zod. Возвращает 400 с flatten-ошибками. |
| `errorHandler` | Глобальный обработчик ошибок: логирует через Winston, отвечает статусом ошибки либо 500. |

### 4.2 API-маршруты

#### `/api/auth`

| Метод | Путь | Auth | Описание |
|---|---|---|---|
| POST | `/login` | — | Логин. Body: `{ email, password }`. Ответ: `{ accessToken, refreshToken, user }`. |
| POST | `/refresh` | — | Обновить токен. Body: `{ refreshToken }`. Ответ: `{ accessToken }`. |
| GET | `/me` | ✓ | Профиль текущего пользователя. |
| POST | `/password` | ✓ | Смена СВОЕГО пароля: `{currentPassword, newPassword}` (новый — от 8 символов). 422 `WRONG_PASSWORD` / `SAME_PASSWORD`. Ответ: 204. Прежние токены не отзываются — блеклиста нет (§7). Аудит `user.password_change`. |
| DELETE | `/logout` | ✓ | Ответ: 204. Ничего не инвалидирует: JWT stateless, токены удаляет клиент (§7). |

JWT реализован через библиотеку `jose`. `accessToken` — короткоживущий, `refreshToken` — долгоживущий.

#### `/api/estimates`

Все маршруты требуют аутентификации.

| Метод | Путь | Роли | Описание |
|---|---|---|---|
| GET | `/` | все | Список расчётов. ADMIN, MANAGER и VIEWER видят все, остальные — свои. |
| POST | `/` | ENGINEER+ | Создать standalone-расчёт. Body: `{ title, deviceType, surveyData? }`. Аудит `estimate.create`. |
| GET | `/:id` | все | Расчёт с последним снапшотом. ADMIN, MANAGER и VIEWER — любой, остальные — только свой. |
| PATCH | `/:id/survey` | ENGINEER+ | Обновить `surveyData` (merge с существующим, тело валидируется Zod). `totals.salePriceRub` переносится в колонку `totalRub`. Из `DRAFT` переводит в `CALC`, остальные статусы не трогает. 422 `ESTIMATE_FROZEN` для APPROVED, `ESTIMATE_REJECTED` для REJECTED. |
| PATCH | `/:id/status` | ENGINEER+ | Смена статуса. Таблица переходов — см. §4.3. |
| DELETE | `/:id` | все | Только DRAFT / CALC / REJECTED и только пока по расчёту нет снапшотов (иначе 422 `ESTIMATE_HAS_SNAPSHOTS`: снапшоты подтверждают цену, ушедшую заказчику). Проверка: автор или ADMIN. Ответ: 204. |
| POST | `/:id/snapshot` | ENGINEER+ | Ручная фиксация версии. Тело необязательно — по умолчанию снимается текущее состояние расчёта. Версия = `MAX(version) + 1`, берётся внутри транзакции. Аудит `estimate.snapshot`. |
| GET | `/:id/snapshots` | все | История версий (без содержимого деревьев — они тяжёлые). |
| POST | `/:id/kp` | ENGINEER+ | Выпуск КП: гейт «нет строк без цены» (422 `ROWS_WITHOUT_PRICE` со списком строк) + снапшот. Аудит `estimate.kp`. |
| GET | `/:id/kp/export` | все | Печатная форма выпущенного КП: `?format=docx\|pdf`, `?version=N` (по умолчанию последняя редакция). Документ строится **из снапшота**, а не из текущего дерева. Количества в спецификации — **на весь тираж**, как и цена (§9.1). Снапшотов нет — 422 `KP_NOT_ISSUED`; количество хотя бы одной строки не определено — 422 `KP_SPEC_INCOMPLETE` (лечится пересохранением расчёта и новым выпуском). Аудит `estimate.kp.export`. |
| POST | `/:id/purchase-request/export` | ENGINEER+, BUYER | Заявка на закупку в .xlsx (§9.6). Строки считает фронтенд и присылает в теле: движок расчёта один, дублировать его на бэкенде значило бы получить расхождение. Аудит `purchase.export`. |

### 4.3 Таблица переходов статусов расчёта

> **v1.5, уточнено заказчиком 2026-07-16 — реальный бизнес-процесс.**
> Подтверждение расчёта внутри калькулятора **не требуется**: согласование
> проходит над **печатной формой КП**, в коммерческом отделе, **мимо
> калькулятора**. Реальный процесс:
>
> ```
> Предварительный расчёт → КП → согласование КП в коммерческом отделе (вне системы)
>    → дальнейшая проработка инженером (трубы, оборудование, насосы, детали)
>    → сметы, спецификации, списки для ERP, закупка        ← не проработано
> ```
>
> **Ключевое следствие: расчёт НЕ замораживается.** Инженер продолжает править
> его *после* выпуска КП — это следующий шаг процесса, а не нарушение. Прежнее
> требование «APPROVED замораживает расчёт» (Механика §10) противоречит
> процессу и отменено.
>
> **Следствие для API (решение 2026-07-20).** Согласование через статусы
> удалено: рабочих статусов два — `DRAFT` и `CALC`. `REVIEW` и `APPROVED`
> остаются в enum БД только ради ранее сохранённых расчётов; попытка перевести
> расчёт в любой из них отклоняется — `422` с кодом `STATUS_FLOW_REMOVED`.
> Кнопок смены статуса в UI нет.
>
> **Точка фиксации — выпуск КП**, а не смена статуса: снапшот снимается при
> формировании КП и фиксирует, из каких цен и какой версии прайса родилась
> цифра в согласуемом документе. Красные строки (без цены) блокируют выпуск КП
> (`422 ROWS_WITHOUT_PRICE`). Печатная форма строится из снапшота, а не из
> текущего дерева: расчёт после выпуска КП продолжает правиться.

Таблица переходов (реализована целиком):

| Из | В | Минимальная роль |
|---|---|---|
| DRAFT | CALC | ENGINEER — явным `PATCH /:id/status` либо автоматически при первом `PATCH /:id/survey` |
| любой | REJECTED | ADMIN |

Всё остальное — `422`: переходы в `REVIEW` и `APPROVED` отклоняются кодом
`STATUS_FLOW_REMOVED`, прочие сочетания — сообщением «Переход X→Y недопустим
для роли Z».

Унаследованные статусы блокируют правку: `PATCH /:id/survey` отвечает `422`
`ESTIMATE_FROZEN` на APPROVED и `ESTIMATE_REJECTED` на REJECTED.

### 5.2 HTTP-клиент — `api/client.ts`

Axios-инстанс с двумя интерсепторами:

- **Request interceptor:** добавляет заголовок `Authorization: Bearer <token>` из `localStorage`. Для `FormData` (импорт прайса) снимает дефолтный `Content-Type`, иначе браузер не проставит `boundary` и multer не увидит файл.
- **Response interceptor (401):** однократно (`_retry`) пытается обновить `accessToken` через `POST /api/auth/refresh` токеном из `localStorage ('ntt_refresh')`; параллельные 401 ждут один и тот же запрос обновления. При неудаче — очищает `localStorage` и перенаправляет на `/login`.

### 5.6 Опросный лист — `/survey/:id?`

Полноэкранный маршрут, а не модал: `SurveyView` выбирает ветку по типу изделия (`SurveyKnsView` / `SurveyEmkView` / `SurveyKolView`) поверх общего каркаса `SurveyShell` (топбар, степпер секций, live-панель авторасчётов). Вход из карточки проекта — кнопка добавления единицы → `/survey?project=<id>`; расчёт создаётся `POST /api/projects/:id/estimates` **по завершении** листа, а не при его открытии, после чего пользователь переходит в калькулятор. У существующего расчёта тип изделия зафиксирован — переключатель типа не выводится.

**Секции по типу устройства** (состав полей — по реальным опросным листам, см. `Реверс_калькуляторов.md`):

**KNS — Насосная станция.** КНС, ЛНС и ДНС конструктивно идентичны — это один тип изделия с одним шаблоном расчёта. Различия только в ТЗ на проектирование и среде стока, что фиксируется полем «Тип НС» (влияет на подписи и значения входов, не на структуру):
- Общие: № заявки ОЛ, тип НС (Канализационная / Ливневая / Дренажная / Водопроводная), стадия проекта, заказчик, объект, регион, дата (`SurveyCommonForm`, `types/survey.ts`)
- Корпус: DN (300–3000 мм, шаг из справочника), глубина подземной части L мм (ручной ввод ИЛИ авторасчёт от глубины лотка и рабочих уровней), возвышение над землёй мм, под проезжей частью (да/нет), по ТТ МВК (да/нет)
- **PN/SN — вычисляемые с override** (решение дизайн-сессии, подтверждено всеми 6 реальными ОЛ; правило SN уточнено заводом): PN = 0,1 (безнапорный корпус); ступеней жёсткости реально две — глубина > 7000 мм → **10000**, иначе **5000**; флаг «под проезжей частью» поднимает на ступень. Чекбокс «изменить вручную» открывает селекты PN/SN
  > **Обозначение по ТТ МВК ≠ расчётная жёсткость.** По требованиям МВК труба маркируется как **8000** вместо 5000 и **12000** вместо 10000 — это то же изделие с двумя дополнительными нитками ровинга, по массе и габаритам одинаковое. Обозначение идёт только в марку трубы (`Труба СК/НПС-К {DN}-{PN}-{SN}`), а вес и трудоёмкость считаются по расчётной жёсткости. **Автоподбор** после перехода на правило завода даёт только {5000; 10000} (`engines/survey-kns.ts`, `snByDepth`) — прежние ступени 1250 и 2500 он не выдаёт. Ручной override при этом по-прежнему предлагает все четыре ступени (`SN_LIST` в `views/SurveyKnsView.vue:346`, то же в `SurveyEmkView.vue:240` и `SurveyKolView.vue:236`), и выбранное значение уходит прямо в `derived.sn` (`composables/usePipeOverride.ts:23-25`), поэтому промах по справочнику весов остаётся достижим вручную (§9.4).
  > Та же матрица реализована на бэкенде — `POST /api/pump-station/ring-stiffness`, где входом служит глубина подводящего патрубка плюс запас 2 м, а порог тот же (7 м, граница относится к нижней ветке)
- Патрубки: для подводящего и напорного — материал трубы (ПЭ / ПВХ / ПНД / ПП / Асбестцемент / Корсис / стеклокомпозит), DN мм, кол-во, глубина залегания лотка мм (у подводящего обязательна — из неё считается Нподз); арматура на подводящем (да/нет), аварийный трубопровод (да/нет)
- **Кол-во арматуры — вычисляемое с override** (решение дизайн-сессии, сходится с 5 из 6 реальных ОЛ; расхождение — нестандартный объект 340 л/с, закрывается override): задвижки (безнапорные) = кол-во подводящих × флаг «арматура на подводящем»; шаровые краны (напорная линия) = (раб + рез) + 1 коллектор + 1 при аварийном трубопроводе
- Насосное: максимальный приток (л/с | м³/ч | м³/сут), расчётный напор м, марка насосов, кол-во рабочих / резервных / запасных, взрывозащита (да/нет). Высота рамы и минимальный уровень жидкости в форму не вынесены: в подборе глубины это константы `DEFAULT_FRAME_H_M = 0,16` и `DEFAULT_MIN_LEVEL_M = 0,627` (`engines/survey-kns.ts`)
- Авторасчёт объёмов (из ОЛ): `Vэф = Q·3,6/(4·пусков_в_час·n_раб)`, `Vмин = (Q·3,6/n_раб)·5/60`, `hраб = 4·Vмин/(π·DN²)`, `Нподз = ROUNDUP((глубина_лотка + hраб + 0,3 + h_рамы + h_мин)·1000; −2)`
  > **Уточнено по прототипу.** `hраб` считается от **Vмин**, а не от «Vраб», как значилось в прежней редакции: только так воспроизводится контрольное число (ОЛ3487: Q 25,13 л/с · DN 3000 · n 2 · лоток 9910 мм → Нподз 11 600 мм). «Vраб» в расчёте не участвует. Реализация — `engines/survey-kns.ts`, `computeDepth`; константы: пусков в час 10, минимальный цикл 5 мин, запас 0,3 м
- Доп. оборудование: дробилка / корзина / обе / нет; ШУ (да/нет + тип внутренний/уличный, пуск стандартный/плавный/ЧП), датчики давления, датчики уровня, расходомер
- Теплоизоляция (да/нет + глубина мм). Поля вентиляции у КНС нет: вентстояк входит в шаблон безусловно, Ø в ОЛ не задаётся — типовой ПЭ Ду110 (`engines/template-kns.ts`, `buildVent`)

> Поля реальных бумажных ОЛ, которых в форме пока нет (смола и вид стоков, направление патрубков в часах, тип соединения и тип запорной арматуры, трубопровод взмучивания, DN автоматической трубной муфты, ввод питания и модуль диспетчеризации ШУ, назначение ОЛ), перечислены в §7.

**EMK — Ёмкостное изделие:**
- Общие поля как у KNS; тип ёмкости (Накопительная / Химстойкая / Аккумулирующая / Питьевая / С насосным оборудованием) — химстойкая переключает материал СК/НПС → СК/ВЭС
- Габариты: объём м³, DN (селект), расположение (горизонтальное/вертикальное), установка (наземная/подземная/в помещении). DN — вход, а не авторасчёт; из объёма и DN считается длина трубы `CEILING(4V/(π·(DN/1000)²)·1000; 100)` с ручным override, у горизонтальной ёмкости габаритная длина +1500 мм на эллиптические днища. Возвышение — не таблица, а две ветки: подземная 300 мм, иначе 0. Из листа «для шапки» взяты только возвышение и параметры шахты обслуживания (8 комбинаций); сам лист как справочник габаритов не годится — в нём числа конкретного заказа (`engines/survey-emk-kol.ts`). PN, SN (SN — по габаритной длине, той же лестницей, что у КНС)
- Шахта обслуживания (да/нет, d, h), лестница. Диапазон d ничем не ограничен: поле `shaftD` — свободный числовой ввод (`views/SurveyEmkView.vue:84`), а движок для расчёта берёт фиксированный Ø1200 (`engines/survey-emk-kol.ts:72`)
- Патрубки подводящий/отводящий: материал, DN, кол-во, глубина залегания лотка
- Насосное оборудование (да/нет) — при «да» гидравлический блок как у KNS
- Дробилка/корзина, запорная арматура, ШУ + датчики, вентиляция, теплоизоляция

**KOL — Колодец:**
- Общие поля; тип колодца (в т.ч. гаситель)
- Корпус: DN рабочей части, PN, SN, глубина H мм, возвышение, под проезжей частью, горловина (да/нет + d + h)
- Лестница (да/нет), смола (тип → марка), вид стоков
- Патрубки подводящий/отводящий: материал, глубина залегания лотка, DN, кол-во
- Доп. оборудование: дробилка/корзина, запорная арматура, ШУ, датчики; теплоизоляция (да/нет + глубина)

**Единый контракт сохранения** (одинаков для всех трёх изделий, `PATCH /api/estimates/:id/survey`):

| Ключ `surveyData` | Содержание |
|---|---|
| `common` | Общий блок для экранов, не знающих тип изделия (заказчик, объект, № заявки и т.п.) |
| `kns` / `emk` / `kol` | Параметры материализации по типу изделия. Шаблон выбирается по `Estimate.deviceType`, а не по наличию ключа: если ключа для этого типа нет, `materializeByDevice` возвращает `null` и экран показывает «В расчёте нет параметров ОЛ… — заполните опросный лист» (`stores/calcTree.ts`) |
| `form` | Полная форма ОЛ — для повторного открытия листа |
| `derived` | Авторасчёты ОЛ (КНС): `npodzMm`, `sn`, `pn`, `pipeGrade`, `fullHeightMm`, `gates`, `balls` |
| `surveyRev` | Ревизия ОЛ, растёт при каждом сохранении — маркер «ОЛ изменился» для рематериализации дерева (§5.1) |

Поля-флаги опросного листа управляют включением разделов шаблона расчёта (см. §9).

## 6. Конфигурация окружения

### Backend — `backend/.env` (образец: `backend/.env.example`)

```env
DATABASE_URL=postgresql://ntt:secret@localhost:5432/ntt_estimates
NODE_ENV=development
PORT=3000
CORS_ORIGIN=http://localhost:5173
JWT_SECRET=<secret>
JWT_ACCESS_EXPIRES=15m
JWT_REFRESH_EXPIRES=7d
```

Отдельного `REFRESH_SECRET` нет и быть не может: access- и refresh-токены подписываются и проверяются одним `JWT_SECRET` (`utils/jwt.ts`), различаются только сроком жизни. `CORS_ORIGIN` принимает список источников через запятую; `*` разрешает любой.

### Frontend — `ntt-calculator/.env` (образец: `ntt-calculator/.env.example`)

```env
VITE_API_URL=http://localhost:3000/api
VITE_APP_VERSION=0.2.0
```

### Docker — `.env` в корне (образец: `.env.example`)

Читается только `docker-compose.yml` (nginx + backend + PostgreSQL); на запуск без Docker не влияет.

```env
POSTGRES_USER=ntt
POSTGRES_PASSWORD=<обязателен>
POSTGRES_DB=ntt_estimates
JWT_SECRET=<обязателен>
HTTP_PORT=80
PUBLIC_URL=http://localhost
```

Compose собирает из них backend-окружение и подставляет `PUBLIC_URL` в `CORS_ORIGIN`; фронтенд собирается с `VITE_API_URL=/api`. Пошаговый порядок развёртывания — `РАЗВЁРТЫВАНИЕ.md`.

Переменные Битрикс24 (`B24_DOMAIN`, `B24_CLIENT_ID`, `B24_CLIENT_SECRET`) появятся вместе с интеграцией (§10) — в коде их сейчас нет. Для неё же `PUBLIC_URL` должен указывать на постоянное доменное имя с валидным TLS (§10.1).

## 9. Модель расчёта изделия (по реверсу реальных калькуляторов)

Раздел добавлен в v1.1 по результатам анализа 6 реальных файлов. Полные формулы и карты разделов — в `doc/Реверс_калькуляторов.md`.

### 9.1 Принцип: шаблон + overrides, а не свободное дерево

Реальный расчёт — не свободное дерево, а **шаблонная спецификация изделия** (BOM + нормирование труда): фиксированный каркас, количества вычисляются формулами из опросного листа, цены подтягиваются из прайса, инженер точечно переопределяет количества и цены:

- Шаблон изделия = **сборка верхнего уровня** (рекурсивный узел каталога с биндингами параметров на поля ОЛ). Для КНС/ЛНС — 7 сборок-разделов: Корпус, Лестница, Перекрытие/площадка/балки, Вентиляционный стояк, Напорный трубопровод, Крепёж, Оборудование и запорная арматура. Для ЕМК — 8 разделов (добавляется «Корзина»), для КОЛ — 7 (есть «Корзина», нет «Напорного трубопровода»); каркасы заданы в `engines/template-kns.ts` и `engines/template-emk-kol.ts`.
- Узел/сборка имеет **флаг включения** (управляется полем ОЛ или вручную): выключен → количества = 0, узел не влияет на итог.
- При создании расчёта из ОЛ шаблон материализуется в строки; далее инженер добавляет/удаляет строки (прежде всего в «Напорном трубопроводе» и «Оборудовании» — их длина сильно варьирует между заказами).
- КНС/ЛНС/ДНС — один шаблон: конструктивно изделия идентичны, тип НС (среда стока) — атрибут расчёта, влияющий на наименования и входы, не на структуру.
- Шаблоны декомпозируются на **переиспользуемые компоненты** (обечайка, днище, патрубок, теплоизоляция, петли, лестница, перекрытие, вентстояк, нитка напорного трубопровода, насосная группа и т.д. — каталог из ~26 узлов в `doc/Библиотека_компонентов.md`); формулы одних и тех же узлов идентичны во всех трёх калькуляторах. Нестандартные изделия собираются из компонентов без шаблона; собранная конфигурация сохраняется как новый шаблон (роль TECHNOLOG, редактор каталога — фаза 3).
- Модель каталога (целевая): единая рекурсивная сущность `NodeDef` (компонент = узел-лист, сборки из сборок), флаги вместо классов, формулы — реестр функций в коде, дерево расчёта — Json-документ с материализацией (см. §4 и §6 библиотеки). Трассируемость цены — фиксацией применённых цен/ставок в строках расчёта + версия прайса. **Реализовано частично:** дерево-Json, материализация, реестр формул и фиксация цен работают; самой сущности `NodeDef` в схеме нет — каркас шаблона задан кодом (§7).

### 9.3 ФОТ-строки

К каждой производственной операции автоматически добавляется парная строка ФОТ. Трудоёмкость = **масса операции (кг) × коэффициент**:

| Вид операции (по вхождению в наименование) | Коэффициент, чел.ч/кг |
|---|---|
| `*мех*` (механическая формовка) | 0,28 |
| `*ламин*` (ламинирование) | 0,56 |
| прочее (ручная формовка, отдельные ламинирования) | 1,0 |

`qty = ROUNDUP(масса × k; 0,1)`; цена = ставка ФОТ из прайса (позиция «ФОТ/ФОТ/чел. ч»). ФОТ — производная строки-операции: независимый ввод запрещён, ручной override возможен (см. `Библиотека_компонентов.md` §1.1).

### 9.4 Формулы количеств (движок шаблона)

Количества строк шаблона вычисляются из ОЛ и справочников. Базовые константы: плотность ламината **1850 кг/м³**, норма ламинирования детали к корпусу **3/10 массы детали**, прорезка отверстия **0,5 чел.ч на 1 м окружности**, «придание товарного вида» **DN/1300 чел.ч на 1 м трубы**. Примеры:

- вес трубы корпуса: `L × вес_пм(DN;PN_трубы;SN)` из справочника весов;
  > **v1.5, уточнено по первоисточнику.** В расчёте участвуют **две разные PN**, их нельзя путать:
  > - `PN_ОЛ` (ячейка `G8 = ОЛ!E21`, для КНС = 0,1 — безнапорный корпус) — идёт **только в наименование** («Труба СК/НПС-К 3000-0,1-10000»);
  > - `PN_трубы` (ячейка `F7`, **автоподбор по таблице весов**) — идёт **только в ключ поиска веса**.
  >
  > Логика `F7`: если `PN_ОЛ > 0,6` и пара (DN;SN) входит в спецсписок → `1,6`; иначе если `DN = 1300` и `SN ∈ {5000, 10000}` и `PN_ОЛ ≤ 0,4` → `0,4`; иначе если `PN_ОЛ ≤ 0,6` → `0,6`; иначе `1`.
  >
  > Домены таблицы весов: `PN ∈ {0,6; 1; 1,6}`, `SN ∈ {2500; 5000; 10000}`, `DN` 300…3000 (162 строки). **`PN_ОЛ = 0,1` в таблице весов отсутствует** — искать по нему нельзя, для того и нужен `PN_трубы`. **Автоподбор** `SN` промахов больше не даёт: после перехода на правило завода его домен — {5000; 10000} (§5.6), а обозначения 8000/12000 по ТТ МВК в поиск веса не идут. Ручной override SN промах допускает: селект предлагает и `1250`, которого в таблице весов нет (§5.6). Для ОЛ3487: ключ `3000;0,6;10000` → 970,2 кг/пм.
  >
  > **❓ Дефект первоисточника:** ветка `F7 → 0,4` недостижима в таблице весов (`PN = 0,4` там нет) — поиск даст промах. Требует уточнения у завода.
- **Гильза патрубка** (`K8`/`M8`): `IF(DN ≥ 200; CEILING(DN+100; 100); CEILING(DN+100; 50))`, причём при `DN < 100` надбавка +100 не применяется.
- масса формованного дна: `π·((DN+300)/2000)²·0,01·1850 + ((DN/1000)²·π·0,008·1850)/4`;
- теплоизоляция: `π·(DN/1000)·h_ти` м² (вертикаль) + `π·(DN/2000)²` (крышка), защитный слой `S·0,005·1850` кг;
- анкеры: `(глубина·1000·9,8·π·Дн²/4)/27500`, шт.

Полный перечень — в отчёте по реверсу. Формулы хранятся в шаблоне (engines/), не в данных.

### 9.5 Экономический итоговый блок

Единый для всех типов изделий (проценты подтверждены во всех 6 файлах):

1. Σ чел.ч по участку фитингов и участку РМУ (разделение по `*изготов*` в наименовании работы)
2. ФОТ на ПЗР = `ROUNDUP(часы_фитингов / 11; 0,1)` × ставка ФОТ
3. Ацетон = `ROUNDUP(масса_формовки_кг × 0,05; 0,1)` × цена ацетона
4. СИЗ и РМ = `ROUNDUP(часы_фитингов + 302)` × цена СИЗ, ЕИ = `ед.`
   > **v1.5, уточнено по первоисточнику** (`Шаблон 3.0.xlsx`, лист «Калькулятор КНС», ячейка `J446: =ROUNDUP(J441+302,)`). Ранее здесь было `часы_фитингов + ПЗР` — это не соответствует эталону: ПЗР в формуле СИЗ **не участвует**, а `302` — захардкоженная в шаблоне константа. Расхождение подтверждено и реализуется «как в эталоне» (решение от 2026-07-16).
   > **❓ ТРЕБУЕТ УТОЧНЕНИЯ У ЗАВОДА:** физический смысл константы 302 (комплекты СИЗ? фиксированная норма на изделие?) и её зависимость от типа/размера изделия. Пока вынесена в именованную константу настроек `SIZ_BASE_UNITS = 302`.
5. Накладные = `(часы_фитингов + ПЗР)` × **ставка накладных** (руб/чел.ч, из прайса; актуальная 1584,73)
6. **Себестоимость (с НДС)** = Труба/муфта + Формовка + Работы ФОТ + Материалы на закупку + Прочие. ПЗР (п. 2) входит в корзину «Работы, ФОТ» (эталон N453), а «Прочие» — это ацетон + СИЗ + накладные (п. 3+4+5, эталон N455). НДС отдельно не выделяется — цены прайса с НДС; печатная форма КП выделяет его «в том числе» справочно (§4.2)
7. **Наценка** — коэффициент, по умолчанию **0,43** (редактируемый)
8. **Цена продажи** = `ROUNDUP(себестоимость × (1 + наценка); до 100 ₽)`
9. **Рентабельность** = (цена − себестоимость)/цена (справочно, ~30%)

Поддержка тиража: поле «Корпусов» в итоговом блоке; при ≥2 главные цифры — за весь тираж (количества в таблице умножены на N), а отдельной строкой ниже показывается «за 1 корп.» — цена одного корпуса отдельным прогоном экономики с `tirage = 1` (`views/CalculatorTreeView.vue`). Строки «за N корп.» в интерфейсе нет.

### 9.6 Заявка на закупку

Отчёт-представление поверх расчёта (не отдельная сущность данных): все непустые закупаемые строки (isPurchase = да) с колонками № / Категория / Наименование / ЕИ / Кол-во / Бюджетная цена / Бюджетная стоимость / Дата закупки / Отметка об исполнении.

Экран — `/calculator/:id/purchase`, выгрузка — `POST /api/estimates/:id/purchase-request/export` в .xlsx. Строки считает фронтенд и присылает готовыми: движок расчёта с двухканальным override и парсером арифметики живёт там и покрыт тестами, а вторая реализация тех же формул на бэкенде дала бы расхождение. Это внутренний закупочный документ, а не цена заказчику — точка фиксации цены остаётся снапшотом при выпуске КП (§4.3).

### 9.7 Гидравлический расчёт (модуль подбора насоса)

- Входы: расход на нитку `Q = приток/(3,6 · n_ниток)`, отметки (планировка, ввод, вывод, мин. уровень, диктующая точка), диаметры/длины напорного трубопровода.
- `Hгеом = отметка_дикт − мин_уровень + h_рамы`; потери по длине + местные; `Hтр = Hгеом + ΣHпот + 1 м (излив)`.
- Кривая системы `H = Hгеом + S·Q²`, где `S = (Hтр − Hгеом)/Q²`; кривая насоса — паспортные точки Q–H (ручной ввод); рабочая точка = пересечение. График обеих кривых.
- Результат (марка, кол-во насосов, мощность) записывается в ОЛ и влияет на раздел «Оборудование».

**Реализовано** на бэкенде (`/api/pump-station/*`, §4.2). Первые два подключены к опросному листу КНС (`composables/usePumpSelection.ts`): марка насоса идёт в расчёт через `derived.pumpModel`, диаметр напорного показывается подсказкой. Габарит станции фронт по-прежнему считает своей копией формул (§5.6):

- **Диаметр напорного трубопровода** (`utils/pipe-hydraulics.ts`): `D = √(4·Q/(π·Vрасч))` с округлением вверх до типоразмера ПЭ-100 SDR17; `Vрасч` по умолчанию 1,5 м/с. Расход берётся **на один насос** (`Q / n_раб`): внутренний напорный трубопровод КНС — отдельный подъёмный участок на каждый насос. Возвращаются также теоретический диаметр, фактическая скорость и предупреждения.
- **Подбор марки насоса** (`utils/pump-selection.ts`): по рабочей точке одного насоса — расход делится на число рабочих, напор не делится (параллельные насосы создают один и тот же напор). Отбор идёт по ПАСПОРТНОЙ КРИВОЙ: `utils/pump-curve.ts` интерполирует характеристику `PumpCurvePoint` при требуемом расходе, и насос годится, если даёт там напор не меньше требуемого. Требуемый запас по напору — окно 0,5…2,0 м: нижняя граница жёсткая (реальный насос может не выдать паспорт), верхняя — предпочтение (сверх неё машина просто крупнее нужного). Из подходящих берётся наименьший достаточный: сначала попавшие в окно, внутри группы — с минимальной мощностью на валу. Все подходящие отдаются в `candidates` для выбора вручную, дотянувшие до напора без нужного запаса — отдельно в `belowMargin`. Границы окна настраиваются через `minHeadMarginM` / `maxHeadMarginM`. У пяти моделей DN50/DN65 кривых нет, для них осталась грубая проверка по диапазонам с пометкой `APPROXIMATE_MATCH`.
- **Габарит станции** (`utils/pump-station-dimensions.ts`): подбор диаметра корпуса из типоряда 1800…3200 мм (при ТТ МВК — не меньше 2600) и Нподз по тем же формулам, что в live-панели ОЛ (§5.6), с предупреждениями о выходе за диапазон.

Не реализованы кривая системы, паспортная кривая насоса и график их пересечения — см. §7.

### 9.8 Требования к валидации (из «Инструкций» Excel)

- Редактируемые только «белые» поля (входы и overrides); вычисляемые — read-only с индикацией источника (формула/прайс).
- Категории строк — только из фиксированного списка; наименования собственного производства — из генераторов.
- Запрет символа `~` в наименованиях (наследие VLOOKUP). Реализован на входе данных: строка со «`~`» отбраковывается и при извлечении справочников (`backend/tools/extract-refs.ts:93`), и при импорте прайса (`backend/src/utils/nn-sheet.ts:103`, вызывается из `routes/prices.routes.ts:116`). В редакторе шаблонов и в ручном вводе наименования проверки нет.
- При отсутствии цены в прайсе строка подсвечивается («заполнить стоимость трубы» — типовое место ручного ввода).

## 10. Интеграция с Битрикс24 (облачная версия)

Конечная версия сервиса встраивается в облачный Битрикс24 компании как вкладка/инструмент. Сам сервис физически размещён на локальном сервере компании с выходом в интернет.

### 10.1 Схема развёртывания

```
Браузер пользователя ── https://portal.bitrix24.ru (облако)
        │                        │ iframe (placement)
        │                        ▼
        └────────────► https://calc.<домен-компании>  ← локальный сервер
                                 │
                    nginx (reverse proxy, TLS) → backend (Express :3000) → PostgreSQL
                                 ▲
        Серверы Bitrix24 ────────┘  (OAuth-события, вебхуки)
```

Требования к локальному серверу:

| Требование | Описание |
|---|---|
| Публичный HTTPS-URL | Постоянное доменное имя + валидный TLS-сертификат (Let's Encrypt / certbot). Обязательное условие Битрикс24: обработчик приложения должен быть доступен по HTTPS **до** регистрации приложения на портале |
| Доступность | Из браузеров пользователей (iframe грузится клиентом) и с серверов Bitrix24 (OAuth, события). Белый IP или проброс 443 через роутер; при сером IP — туннель (Cloudflare Tunnel и т.п.) |
| Развёртывание | docker compose: nginx + backend + PostgreSQL; автозапуск, бэкапы БД, UPS |
| Отказоустойчивость | При недоступности локального сервера вкладка в Б24 не откроется — мониторинг доступности (uptime-проба) обязателен |

### 10.2 Форма интеграции: локальное приложение Битрикс24

Регистрируется на портале как **локальное (местное) приложение** — «серверное приложение с интерфейсом» (*Приложения → Разработчикам → Другое → Локальное приложение*), без публикации в Маркете. Портал выдаёт `client_id` / `client_secret`; приложение получает REST-доступ по OAuth 2.0 в правах текущего пользователя.

Точки встройки (placements):

| Встройка | Механизм | Назначение |
|---|---|---|
| Пункт в левом меню / раздел «Приложения» | Страница приложения по умолчанию | Полный интерфейс сервиса (Dashboard, Калькулятор, Прайс, Админ) |
| Вкладка в карточке сделки | `placement.bind` → `CRM_DEAL_DETAIL_TAB` | Проекты/расчёты, привязанные к сделке; создание расчёта из сделки |
| Вкладка в карточке компании | `CRM_COMPANY_DETAIL_TAB` (опционально) | Все проекты заказчика |

Фронтенд подключает `//api.bitrix24.com/api/v1/` (библиотека BX24) для `BX24.fitWindow`, `BX24.resizeWindow` и получения контекста плейсмента.

### 10.3 Авторизация и SSO

1. При открытии iframe Битрикс24 передаёт POST: `AUTH_ID` (access token), `REFRESH_ID`, `DOMAIN`, `member_id`, `PLACEMENT`, `PLACEMENT_OPTIONS` (для вкладки сделки — ID сделки).
2. Бэкенд валидирует токен запросом `user.current` к порталу, получает профиль пользователя Б24.
3. По `b24UserId` находится/создаётся локальный пользователь → выдаётся собственный JWT (существующий механизм §4 не меняется). Прямой вход по email/паролю (вне Б24) сохраняется как запасной.
4. Маппинг ролей: администратор портала → `ADMIN`; остальные — по настраиваемой таблице соответствия (подразделение/группа Б24 → роль приложения), по умолчанию `ENGINEER`.

Требования к отдаче фронтенда (работа внутри iframe):
- не отправлять `X-Frame-Options: DENY/SAMEORIGIN`; CSP: `frame-ancestors https://*.bitrix24.ru https://*.bitrix24.com <домен портала>`;
- не полагаться на third-party cookies (Safari/Chrome блокируют в iframe): JWT — в памяти/`localStorage`, не в cookie; если cookie необходимы — `SameSite=None; Secure`.

| User | `b24UserId String? @unique`, `b24Domain String?` |
| Project | `b24DealId String?`, `b24CompanyId String?` |
| Новая: `B24Settings` | `domain`, `clientId`, `clientSecret` (шифрование at rest), `memberId`, маппинг ролей (Json) |
| Новая: `B24Token` | `userId`, `accessToken`, `refreshToken`, `expiresAt` — для фоновых REST-вызовов |

Новые маршруты бэкенда: `POST /api/b24/install` (обработчик установки приложения, сохранение токенов), `POST /api/b24/sso` (обмен AUTH_ID на JWT приложения), `POST /api/b24/events` (обработчик событий), `GET /api/b24/deal-context/:dealId` (данные для вкладки сделки).

### 10.6 Безопасность

- Сервис публично доступен из интернета: обязательны HTTPS, rate limiting, helmet-заголовки, скрытие служебных маршрутов, логирование входов в AuditLog (`b24.sso`, `b24.install`).
- Проверка подлинности запросов от Б24: валидация `AUTH_ID` только серверным вызовом к порталу из `B24Settings.domain`; для событий — сверка `application_token`.
- `client_secret`, `refresh_token` — только на бэкенде, в открытом виде на фронтенд не передаются.
