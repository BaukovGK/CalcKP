# Техническое задание: НТТ Калькулятор стоимости изделий

**Версия:** 1.4 (v1.1 — дополнена по реверс-инжинирингу 6 реальных Excel-калькуляторов, см. `doc/Реверс_калькуляторов.md`; v1.2 — интеграция с Битрикс24, §10; v1.3 — компонентная модель: единый рекурсивный узел каталога, материализация, Json-дерево расчёта, реестр формул в коде, роль TECHNOLOG — см. `doc/Библиотека_компонентов.md`; v1.4 — решения дизайн-сессии: авторасчёт PN/SN и арматуры в ОЛ, дизайн-токены — см. `design_handoff_ntt_calculator/README.md`)
**Стек:** Express 5 + Prisma 7 + PostgreSQL (бэкенд) · Vue 3 + Pinia + Vue Router 5 + Vite (фронтенд)

---

## 1. Назначение системы

Веб-приложение для расчёта стоимости изделий (КНС, ЕМК, КОЛ) в составе инженерных проектов. Основные рабочие процессы:

1. Создание проекта (объект, заказчик, адрес).
2. Добавление к проекту единиц оборудования с заполнением опросного листа.
3. Детальный расчёт стоимости в Калькуляторе: материализация шаблона изделия из опросного листа, тюнинг дерева расчёта (сборки → компоненты → строки) с overrides количеств и цен (§9).
4. Движение расчёта по статусам: `DRAFT → CALC → REVIEW → APPROVED`.
5. Управление прайс-листом (ADMIN / BUYER).
6. Администрирование пользователей, просмотр аудит-лога (ADMIN).

---

## 2. Роли пользователей

| Роль | Доступ |
|---|---|
| `ADMIN` | Полный доступ: пользователи, прайс, каталог, все проекты, смена любого статуса |
| `MANAGER` | Проекты своей команды, расчёты, утверждение (→ APPROVED) |
| `ENGINEER` | Создание/редактирование своих проектов и расчётов |
| `TECHNOLOG` | Редактор каталога типовых компонентов и шаблонов изделий (см. `Библиотека_компонентов.md` §6.2); чтение прайса; без доступа к чужим проектам и администрированию |
| `BUYER` | Только прайс-лист |
| `VIEWER` | Просмотр без изменений |

## 4. Бэкенд

**Точка входа:** `backend/src/app.ts` · Порт: `3000` (env `PORT`)

### 4.1 Middleware

| Middleware | Описание |
|---|---|
| `requireAuth` | Проверяет Bearer JWT. Кладёт `userId`, `userRole` в `req`. Возвращает 401 при невалидном токене. |
| `requireRole(...roles)` | Проверяет роль после `requireAuth`. Возвращает 403. |
| `validate(zodSchema)` | Валидирует `req.body` через Zod. Возвращает 400 с flatten-ошибками. |
| `errorHandler` | Глобальный обработчик ошибок: логирует через Winston, возвращает 500. |

## 5. Фронтенд

**Dev-сервер:** `http://localhost:5173`
**API base URL:** env `VITE_API_URL` (по умолчанию `/api`)

### 5.1 Структура хранилищ (Pinia)

#### `useAuthStore` — `stores/auth.ts`
- **Состояние:** `user` (объект), `accessToken` — персистируются в `localStorage` (`ntt_user`, `ntt_token`).
- **Действия:**
  - `login(email, password)` — POST `/api/auth/login`
  - `loginDemo()` — локальный вход без бэкенда, роль MANAGER
  - `logout()` — очищает токены, DELETE `/api/auth/logout`
  - `refresh()` — POST `/api/auth/refresh`
  - `checkAuth()` — GET `/api/auth/me`, вызывается при первой навигации

#### `useProjectsStore` — `stores/projects.ts`
- **Состояние:** `list: ProjectListItem[]`, `current: ProjectDetail | null`, `loading`, `error`.
- **Действия:** `fetchAll()`, `fetchOne(id)`, `create(dto)`, `addEstimate(projectId, dto)`, `clear()`.
- После `addEstimate` локально обновляет `current.estimates` и запись в `list`.

#### `useEstimatesStore` — `stores/estimates.ts`
- Упрощённое хранилище для standalone-расчётов.
- **Действия:** `fetchAll()`, `fetchOne(id)`, `create(dto)`, `clear()`.

#### `useCalculatorStore` — `stores/calculator.ts`
- **Состояние:** реактивное дерево расчёта. Текущая реализация (фаза 1): `bundles: CalcBundle[]`, `Bundle → Group → Subgroup → Row`. Целевая структура (фаза 2): материализованное дерево `Изделие → Сборки → Компоненты → Строки` (см. §9, `Библиотека_компонентов.md`).
- **Типы строк** (целевые, по реальным калькуляторам):
  - `МАТЕРИАЛ` — закупаемая позиция (категория из 16, ЕИ, цена из прайса / override)
  - `ОПЕРАЦИЯ` — собственное производство: масса/объём, ставка ₽/кг; порождает ФОТ
  - `ФОТ` — производная строка операции: `чел.ч = ROUNDUP(масса × k, 0.1)`, k = 0,28 / 0,56 / 1,0 (см. §9.3); независимый ввод запрещён, override возможен
- **Вычисления** (модуль `engines/cost.ts` + реестр формул): строка → узел → сборка → итог; двухканальный override (кол-во, цена); ФОТ-спутники пересчитываются от итоговой массы родительской операции.
- **CRUD:** узлы дерева и строки; вставка компонентов/сборок из каталога (материализация).
- **DnD:** перемещение строк и узлов через `provide/inject ('dragState')`.
- **Экспорт:** `exportTxt()` — выгрузка расчёта в текстовый файл.

### 5.5 Модуль Калькулятора — подробно

Основной рабочий экран. Данные хранятся в `Estimate.surveyData.bundles`.

> Ниже описана текущая реализация (фаза 1, свободное дерево «связка→группа→подгруппа→строка»). В фазе 2 иерархия отображает материализованное дерево «Сборка→Компонент→Строка» (§9); компонентная структура UI сохраняется, меняется источник дерева и типы строк.

```
CalculatorView
 └─ CalcBundle          (связка — заголовок, цвет, итог по связке)
     └─ CalcGroup       (группа — подзаголовок, итог по группе)
         └─ CalcSubgroup  (подгруппа — таблица строк)
             └─ CalcRow   (строка — тип, наименование, кол-во, ед., цена, сумма)
```

**Взаимодействие между компонентами:**

| Механизм | Назначение |
|---|---|
| `provide/inject 'dragState'` | Состояние DnD (активный элемент, зона сброса) |
| `provide/inject 'showCtx'` | Открыть контекстное меню с набором действий |
| `provide/inject 'openModal'` | Открыть модал настроек связки (название, цвет) |

**Сохранение расчёта:**
`PATCH /api/estimates/:id/survey` с телом `{ bundles: store.bundles }`.
Бэкенд выполняет **merge** с существующими техническими параметрами опросного листа (поля `kns`, `emk`, `kol`), не перезаписывая их.

**Смена статуса:**
Кнопки в topbar адаптируются к текущему статусу и роли пользователя:
- `DRAFT` → «В расчёт» (ENGINEER+)
- `CALC` → «На проверку» (MANAGER+)
- `REVIEW` → «Утвердить» / «← Вернуть» (MANAGER+)

### 5.6 Опросный лист — `SurveyModal`

Открывается при добавлении единицы оборудования (`POST /api/projects/:id/estimates`). Закрытие по клику на фон **отключено** (`closeOnBackdrop: false`).

**Секции по типу устройства** (состав полей — по реальным опросным листам, см. `Реверс_калькуляторов.md`):

**KNS — Насосная станция.** КНС, ЛНС и ДНС конструктивно идентичны — это один тип изделия с одним шаблоном расчёта. Различия только в ТЗ на проектирование и среде стока, что фиксируется полем «Тип НС» (влияет на подписи и значения входов, не на структуру):
- Общие: № заявки ОЛ, тип НС (Канализационная / Ливневая / Дренажная / Водопроводная), назначение ОЛ, заказчик, стадия проекта, объект, регион, дата
- Корпус: DN (300–3000 мм, шаг из справочника), глубина подземной части L мм (ручной ввод ИЛИ авторасчёт от глубины лотка и рабочих уровней), возвышение над землёй мм, под проезжей частью (да/нет), по ТТ МВК (да/нет)
- **PN/SN — вычисляемые с override** (решение дизайн-сессии, подтверждено всеми 6 реальными ОЛ): PN = 0,1 (безнапорный корпус); SN по глубине — >8000 мм → 10000, >5000 → 5000, >3000 → 2500, иначе 1250; флаги «проезжая часть» или «ТТ МВК» поднимают SN на ступень (потолок 10000). Чекбокс «изменить вручную» открывает селекты PN/SN
- Смола: тип (Стандарт / Винилэфирная стандарт / Винилэфирная высокотемп.) → марка (авто), MAX температура, вид стоков
- Патрубки: для подводящего и напорного — материал трубы (ПЭ / ПВХ / ПНД / ПП / Асбестцемент / Корсис / стеклокомпозит), глубина залегания мм, DN мм, направление (в часах), кол-во, тип соединения; тип запорной арматуры, арматура на подводящем (да/нет), аварийный трубопровод (да/нет)
- **Кол-во арматуры — вычисляемое с override** (решение дизайн-сессии, сходится с 5 из 6 реальных ОЛ; расхождение — нестандартный объект 340 л/с, закрывается override): задвижки (безнапорные) = кол-во подводящих × флаг «арматура на подводящем»; шаровые краны (напорная линия) = (раб + рез) + 1 коллектор + 1 при аварийном трубопроводе, трубопровод взмучивания (да/нет)
- Насосное: максимальный приток (л/с | м³/ч | м³/сут), расчётный напор м, марка насосов, кол-во рабочих / резервных / запасных, DN автоматической трубной муфты, взрывозащита (да/нет), мин. уровень жидкости насоса
- Авторасчёт объёмов (из ОЛ): `Vэф = Q/(4·пусков_в_час·n_раб)`, `Vмин`, `hраб = 4·Vраб/(π·DN²)`, `Нподз = ROUNDUP((глубина_лотка + hраб + 0,3 + h_рамы + h_мин)·1000; −2)`
- Доп. оборудование: дробилка / корзина для мусора / оба / нет; ШУ (тип внутренний/уличный, ввод питания, пуск стандартный/плавный/ЧП, модуль диспетчеризации CIM), датчики давления / уровня, расходомер
- Вентиляция (тип), теплоизоляция (да/нет + глубина мм)

**EMK — Ёмкостное изделие:**
- Общие поля как у KNS; тип ёмкости (Накопительная / Химстойкая / Аккумулирующая / Питьевая / С насосным оборудованием) — химстойкая переключает материал СК/НПС → СК/ВЭС
- Габариты: объём м³ + расположение (горизонтальное/вертикальное) + установка (наземная/подземная/в помещении) → авторасчёт DN, длины, возвышения (справочник «для шапки», 8 комбинаций) ИЛИ ручной ввод; PN, SN
- Шахта обслуживания (да/нет, d 700–3000 мм, h), лестница
- Патрубки подводящий/отводящий: материал, DN, кол-во, глубина залегания лотка
- Насосное оборудование (да/нет) — при «да» гидравлический блок как у KNS
- Дробилка/корзина, запорная арматура, ШУ + датчики, вентиляция, теплоизоляция

**KOL — Колодец:**
- Общие поля; тип колодца (в т.ч. гаситель)
- Корпус: DN рабочей части, PN, SN, глубина H мм, возвышение, под проезжей частью, горловина (да/нет + d + h)
- Лестница (да/нет), смола (тип → марка), вид стоков
- Патрубки подводящий/отводящий: материал, глубина залегания лотка, DN, кол-во
- Доп. оборудование: дробилка/корзина, запорная арматура, ШУ, датчики; теплоизоляция (да/нет + глубина)

Данные сохраняются в `surveyData.kns` / `surveyData.emk` / `surveyData.kol`. Поля-флаги опросного листа управляют включением разделов шаблона расчёта (см. §9).

## 9. Модель расчёта изделия (по реверсу реальных калькуляторов)

Раздел добавлен в v1.1 по результатам анализа 6 реальных файлов. Полные формулы и карты разделов — в `doc/Реверс_калькуляторов.md`.

### 9.1 Принцип: шаблон + overrides, а не свободное дерево

Реальный расчёт — не свободное дерево, а **шаблонная спецификация изделия** (BOM + нормирование труда): фиксированный каркас, количества вычисляются формулами из опросного листа, цены подтягиваются из прайса, инженер точечно переопределяет количества и цены:

- Шаблон изделия = **сборка верхнего уровня** (рекурсивный узел каталога с биндингами параметров на поля ОЛ). Для КНС/ЛНС — 7 сборок-разделов: Корпус, Лестница, Перекрытие/площадка/балки, Вентиляционный стояк, Напорный трубопровод, Крепёж, Оборудование и запорная арматура.
- Узел/сборка имеет **флаг включения** (управляется полем ОЛ или вручную): выключен → количества = 0, узел не влияет на итог.
- При создании расчёта из ОЛ шаблон материализуется в строки; далее инженер добавляет/удаляет строки (прежде всего в «Напорном трубопроводе» и «Оборудовании» — их длина сильно варьирует между заказами).
- КНС/ЛНС/ДНС — один шаблон: конструктивно изделия идентичны, тип НС (среда стока) — атрибут расчёта, влияющий на наименования и входы, не на структуру.
- Шаблоны декомпозируются на **переиспользуемые компоненты** (обечайка, днище, патрубок, теплоизоляция, петли, лестница, перекрытие, вентстояк, нитка напорного трубопровода, насосная группа и т.д. — каталог из ~26 узлов в `doc/Библиотека_компонентов.md`); формулы одних и тех же узлов идентичны во всех трёх калькуляторах. Нестандартные изделия собираются из компонентов без шаблона; собранная конфигурация сохраняется как новый шаблон (роль TECHNOLOG, редактор каталога — фаза 3).
- Модель каталога: единая рекурсивная сущность `NodeDef` (компонент = узел-лист, сборки из сборок), флаги вместо классов, формулы — реестр функций в коде, дерево расчёта — Json-документ с материализацией (см. §4 и §6 библиотеки). Трассируемость цены — фиксацией применённых цен/ставок в строках расчёта + версия прайса.

### 9.2 Модель строки

Каждая строка расчёта:

| Поле | Описание |
|---|---|
| category | Одна из 16 категорий: Грузоподъем, Выключатели, Детали труб_да ПЭ ПВХ PPR, Детали трубопровода сталь, Запорная арматура, Металлопрокат, Метизы, Прочее оборудование, Насосы/АТМ, Датчики, Расходомеры, Шкафы, Прочие материалы (закупка) · Собственное производство, Работы, ФОТ (внутренние) |
| name | Наименование; для собственного производства генерируется из параметров (напр. `Труба СК/НПС-К {DN}-{PN}-{SN}`) |
| isPurchase | Вычисляется: категория ∈ закупочным → «да» |
| qtyCalc | Количество по формуле (геометрия/норматив) — read-only |
| qtyManual | Ручной override количества (приоритетен) |
| qty | `qtyManual ?? qtyCalc`, × флаг раздела × кол-во корпусов |
| unit | ЕИ; определяет смысл: `кг` — формовка/ламинат, `чел. ч` — труд |
| priceCatalog | Цена из PriceItem по ключу (category, name, unit) — read-only |
| priceManual | Ручной override цены (приоритетен; для трубы/муфты корпуса цена практически всегда ручная) |
| sum | `qty × (priceManual ?? priceCatalog)` |
| note | Примечание |

### 9.3 ФОТ-строки

К каждой производственной операции автоматически добавляется парная строка ФОТ. Трудоёмкость = **масса операции (кг) × коэффициент**:

| Вид операции (по вхождению в наименование) | Коэффициент, чел.ч/кг |
|---|---|
| `*мех*` (механическая формовка) | 0,28 |
| `*ламин*` (ламинирование) | 0,56 |
| прочее (ручная формовка, отдельные ламинирования) | 1,0 |

`qty = ROUNDUP(масса × k; 0,1)`; цена = ставка ФОТ из прайса (позиция «ФОТ/ФОТ/чел. ч»). ФОТ — производная строки-операции: независимый ввод запрещён, ручной override возможен (см. `Библиотека_компонентов.md` §1.1).

### 9.4 Формулы количеств (движок шаблона)

Количества строк шаблона вычисляются из ОЛ и справочников. Базовые константы: плотность ламината **1850 кг/м³**, норма ламинирования детали к корпусу **3/10 массы детали**, прорезка отверстия **0,5 чел.ч на 1 м окружности**, «придание товарного вида» **DN/1300 чел.ч на 1 м трубы**. Примеры:

- вес трубы корпуса: `L × вес_пм(DN;PN;SN)` из справочника весов;
- масса формованного дна: `π·((DN+300)/2000)²·0,01·1850 + ((DN/1000)²·π·0,008·1850)/4`;
- теплоизоляция: `π·(DN/1000)·h_ти` м² (вертикаль) + `π·(DN/2000)²` (крышка), защитный слой `S·0,005·1850` кг;
- анкеры: `(глубина·1000·9,8·π·Дн²/4)/27500`, шт.

Полный перечень — в отчёте по реверсу. Формулы хранятся в шаблоне (engines/), не в данных.

### 9.5 Экономический итоговый блок

Единый для всех типов изделий (проценты подтверждены во всех 6 файлах):

1. Σ чел.ч по участку фитингов и участку РМУ (разделение по `*изготов*` в наименовании работы)
2. ФОТ на ПЗР = `ROUNDUP(часы_фитингов / 11; 0,1)` × ставка ФОТ
3. Ацетон = `ROUNDUP(масса_формовки_кг × 0,05; 0,1)` × цена ацетона
4. СИЗ и РМ = `ROUNDUP(часы_фитингов + ПЗР)` × цена СИЗ
5. Накладные = `(часы_фитингов + ПЗР)` × **ставка накладных** (руб/чел.ч, из прайса; актуальная 1584,73)
6. **Себестоимость (с НДС)** = Труба/муфта + Формовка + Работы ФОТ + Материалы на закупку + Прочие (2+3+4+5). НДС отдельно не выделяется — цены прайса с НДС
7. **Наценка** — коэффициент, по умолчанию **0,43** (редактируемый)
8. **Цена продажи** = `ROUNDUP(себестоимость × (1 + наценка); до 100 ₽)`
9. **Рентабельность** = (цена − себестоимость)/цена (справочно, ~30%)

Поддержка тиража: поле «кол-во корпусов»; при ≥2 итоги домножаются (вывод «за 1 корп. / за N корп.»).

### 9.6 Заявка на закупку

Отчёт-представление поверх расчёта (не отдельная сущность данных): все непустые закупаемые строки (isPurchase = да) с колонками № / Категория / Наименование / ЕИ / Кол-во / Бюджетная цена / Бюджетная стоимость / Дата закупки / Отметка об исполнении. Экспорт в Excel/PDF.

### 9.7 Гидравлический расчёт (модуль подбора насоса)

- Входы: расход на нитку `Q = приток/(3,6 · n_ниток)`, отметки (планировка, ввод, вывод, мин. уровень, диктующая точка), диаметры/длины напорного трубопровода.
- `Hгеом = отметка_дикт − мин_уровень + h_рамы`; потери по длине + местные; `Hтр = Hгеом + ΣHпот + 1 м (излив)`.
- Кривая системы `H = Hгеом + S·Q²`, где `S = (Hтр − Hгеом)/Q²`; кривая насоса — паспортные точки Q–H (ручной ввод); рабочая точка = пересечение. График обеих кривых.
- Результат (марка, кол-во насосов, мощность) записывается в ОЛ и влияет на раздел «Оборудование».

### 9.8 Требования к валидации (из «Инструкций» Excel)

- Редактируемые только «белые» поля (входы и overrides); вычисляемые — read-only с индикацией источника (формула/прайс).
- Категории строк — только из фиксированного списка; наименования собственного производства — из генераторов.
- Запрет символа `~` в наименованиях (наследие VLOOKUP; в вебе — просто валидация).
- При отсутствии цены в прайсе строка подсвечивается («заполнить стоимость трубы» — типовое место ручного ввода).

## 10. Интеграция с Битрикс24 (облачная версия)

Конечная версия сервиса встраивается в облачный Битрикс24 компании как вкладка/инструмент. Сам сервис физически размещён на локальном сервере компании с выходом в интернет.

### 10.1 Схема развёртывания

```
Браузер пользователя ── https://portal.bitrix24.ru (облако)
        │                        │ iframe (placement)
        │                        ▼
        └────────────► https://calc.<домен-компании>  ← локальный сервер
                                 │
                    nginx (reverse proxy, TLS) → backend (Express :3000) → PostgreSQL
                                 ▲
        Серверы Bitrix24 ────────┘  (OAuth-события, вебхуки)
```

Требования к локальному серверу:

| Требование | Описание |
|---|---|
| Публичный HTTPS-URL | Постоянное доменное имя + валидный TLS-сертификат (Let's Encrypt / certbot). Обязательное условие Битрикс24: обработчик приложения должен быть доступен по HTTPS **до** регистрации приложения на портале |
| Доступность | Из браузеров пользователей (iframe грузится клиентом) и с серверов Bitrix24 (OAuth, события). Белый IP или проброс 443 через роутер; при сером IP — туннель (Cloudflare Tunnel и т.п.) |
| Развёртывание | docker compose: nginx + backend + PostgreSQL; автозапуск, бэкапы БД, UPS |
| Отказоустойчивость | При недоступности локального сервера вкладка в Б24 не откроется — мониторинг доступности (uptime-проба) обязателен |

### 10.2 Форма интеграции: локальное приложение Битрикс24

Регистрируется на портале как **локальное (местное) приложение** — «серверное приложение с интерфейсом» (*Приложения → Разработчикам → Другое → Локальное приложение*), без публикации в Маркете. Портал выдаёт `client_id` / `client_secret`; приложение получает REST-доступ по OAuth 2.0 в правах текущего пользователя.

Точки встройки (placements):

| Встройка | Механизм | Назначение |
|---|---|---|
| Пункт в левом меню / раздел «Приложения» | Страница приложения по умолчанию | Полный интерфейс сервиса (Dashboard, Калькулятор, Прайс, Админ) |
| Вкладка в карточке сделки | `placement.bind` → `CRM_DEAL_DETAIL_TAB` | Проекты/расчёты, привязанные к сделке; создание расчёта из сделки |
| Вкладка в карточке компании | `CRM_COMPANY_DETAIL_TAB` (опционально) | Все проекты заказчика |

Фронтенд подключает `//api.bitrix24.com/api/v1/` (библиотека BX24) для `BX24.fitWindow`, `BX24.resizeWindow` и получения контекста плейсмента.

### 10.3 Авторизация и SSO

1. При открытии iframe Битрикс24 передаёт POST: `AUTH_ID` (access token), `REFRESH_ID`, `DOMAIN`, `member_id`, `PLACEMENT`, `PLACEMENT_OPTIONS` (для вкладки сделки — ID сделки).
2. Бэкенд валидирует токен запросом `user.current` к порталу, получает профиль пользователя Б24.
3. По `b24UserId` находится/создаётся локальный пользователь → выдаётся собственный JWT (существующий механизм §4 не меняется). Прямой вход по email/паролю (вне Б24) сохраняется как запасной.
4. Маппинг ролей: администратор портала → `ADMIN`; остальные — по настраиваемой таблице соответствия (подразделение/группа Б24 → роль приложения), по умолчанию `ENGINEER`.

Требования к отдаче фронтенда (работа внутри iframe):
- не отправлять `X-Frame-Options: DENY/SAMEORIGIN`; CSP: `frame-ancestors https://*.bitrix24.ru https://*.bitrix24.com <домен портала>`;
- не полагаться на third-party cookies (Safari/Chrome блокируют в iframe): JWT — в памяти/`localStorage`, не в cookie; если cookie необходимы — `SameSite=None; Secure`.

### 10.4 Интеграция данных с CRM (REST)

| Сценарий | REST-методы |
|---|---|
| Связь Проект ↔ Сделка: создание проекта из вкладки сделки, автозаполнение заказчика/объекта | `crm.deal.get`, `crm.company.get` |
| Обратная запись итогов: цена продажи утверждённого расчёта → пользовательское поле сделки | `crm.deal.update` (UF-поле «Стоимость по расчёту»), при переходе в `APPROVED` |
| Публикация КП/сметы: экспортированный файл (PDF/Excel) → таймлайн сделки / Диск | `crm.timeline.comment.add`, `disk.folder.uploadfile` |
| Уведомления о смене статуса расчёта | `im.notify.system.add` (опционально) |
| Реакция на изменения сделки | событие `ONCRMDEALUPDATE` (опционально) |

Ограничения облака: только REST (код на стороне портала невозможен), лимит интенсивности запросов (~2 req/s, метод `batch` для пакетных операций), access token живёт 1 час — фоновые операции используют `refresh_token`.

### 10.5 Изменения в модели данных

| Сущность | Дополнение |
|---|---|
| User | `b24UserId String? @unique`, `b24Domain String?` |
| Project | `b24DealId String?`, `b24CompanyId String?` |
| Новая: `B24Settings` | `domain`, `clientId`, `clientSecret` (шифрование at rest), `memberId`, маппинг ролей (Json) |
| Новая: `B24Token` | `userId`, `accessToken`, `refreshToken`, `expiresAt` — для фоновых REST-вызовов |

Новые маршруты бэкенда: `POST /api/b24/install` (обработчик установки приложения, сохранение токенов), `POST /api/b24/sso` (обмен AUTH_ID на JWT приложения), `POST /api/b24/events` (обработчик событий), `GET /api/b24/deal-context/:dealId` (данные для вкладки сделки).

### 10.6 Безопасность

- Сервис публично доступен из интернета: обязательны HTTPS, rate limiting, helmet-заголовки, скрытие служебных маршрутов, логирование входов в AuditLog (`b24.sso`, `b24.install`).
- Проверка подлинности запросов от Б24: валидация `AUTH_ID` только серверным вызовом к порталу из `B24Settings.domain`; для событий — сверка `application_token`.
- `client_secret`, `refresh_token` — только на бэкенде, в открытом виде на фронтенд не передаются.
