## 1. Продукт в одном абзаце

B2B-инструмент расчёта себестоимости и цены промышленных изделий из стеклокомпозита (насосные станции, ёмкости, колодцы) для завода ООО «НТТ». Заменяет Excel-книгу на 19 листов. Инженер заполняет опросный лист изделия — система материализует спецификацию из сотен строк (материалы, операции производства, труд) с формульными количествами и ценами из прайса; инженер точечно «тюнингует» строки; менеджер утверждает; итог уходит в Битрикс24. Ключевое ощущение: **управляю изделием, а не таблицей**.

## 2. Пользователи

| Роль | Портрет | Основной сценарий | Частота |
|---|---|---|---|
| ENGINEER | Инженер-сметчик, глубоко знает изделие, привык к Excel | ОЛ → расчёт → тюнинг → на проверку | ежедневно |
| MANAGER | Руководитель направления | Проверка расчёта, рентабельность, утверждение/возврат | несколько раз в неделю |
| BUYER | Закупщик | Актуализация прайса, заявка на закупку | еженедельно |
| TECHNOLOG | Технолог-методолог | Редактор каталога компонентов и шаблонов (фаза 3) | редко, вдумчиво |
| ADMIN | ИТ/руководство | Пользователи, аудит | редко |

Все — русскоязычные, десктоп, большие мониторы, многочасовые сессии. Мобильная версия не требуется; минимум — читаемость на ноутбуке 1366px.

## 3. Контексты запуска (жёсткое ограничение)

1. **Standalone SPA** — полноэкранный режим.
2. **Iframe внутри Битрикс24** (облако): страница приложения и вкладка в карточке сделки. Следствия: нельзя рассчитывать на всю высоту вьюпорта (resize через BX24 API), нет своих top-level навбаров, дублирующих Б24, нет third-party cookies, вёрстка должна жить в ~900–1200px ширины. Одна и та же вёрстка обслуживает оба контекста — навигация сворачиваемая.

Темизация: светлая и тёмная темы через CSS custom properties (`data-theme` на `<html>`), тёмная — по умолчанию. Все цвета — только токенами.


## 5. Ключевые экраны

### 5.1 Опросный лист (визард)

Анкета изделия, 30–50 полей, секции: общие данные → корпус → смола → патрубки → насосное оборудование → доп. оборудование → вентиляция/теплоизоляция. Требования:

- Прогрессивное раскрытие: флаг «нет» сворачивает зависимые поля (например, «Теплоизоляция: нет» прячет глубину).
- **Live-расчёты рядом с полями:** при вводе расхода и уровней система тут же показывает Vэф/Vмин/Vраб и рекомендуемую глубину подземной части (`Нподз = 11 600 мм`) с возможностью принять или ввести свою. Это фирменный момент продукта — визуально выделить.
- Поля с ЕИ-переключателем (л/с | м³/ч | м³/сут).
- Обязательные поля помечены; черновик сохраняется незавершённым.
- Финал: кнопка «Создать расчёт» с превью: тип изделия, габарит «3000×11900 мм», список включённых блоков.

### 5.2 Калькулятор (главный экран)

Трёхзонная компоновка: слева — дерево сборок (навигация), центр — таблица строк активной сборки, справа/снизу — закреплённая панель итогов.

**Дерево сборок** (7 разделов для НС): каждая с флагом-переключателем включения, подытогом и бейджем проблем. Выключенная сборка — «призрак» (видна, полупрозрачна, в итог не входит). Вложенность до 3–4 уровней: Сборка → Компонент → Строки.

**Таблица строк** — сердце продукта. Колонки: категория · наименование · кол-во · ЕИ · цена · сумма · примечание. Плотность высокая (в реальных расчётах 300–450 строк), но каждая ячейка кол-ва и цены несёт **индикацию источника**:

| Состояние | Индикация | Смысл |
|---|---|---|
| Расчётное значение | серое/обычное | посчитано формулой из ОЛ |
| Ручной override | синий + точка/маркер | инженер переопределил; ховер показывает расчётное значение и кнопку «↺ вернуть» |
| Нет цены | красная строка | цены нет в прайсе и не введена вручную; сумма 0 |
| Конфликт | янтарный значок | ОЛ изменился, расчётное значение «уехало» из-под override; действия: оставить / сбросить |
| Выключено | призрак | сборка/узел выключен |
| ФОТ-спутник | вложена под родителя, слегка отступлена | производная строка; кол-во read-only с override |

- Ввод количества принимает арифметику: `1.55*2+2.88*2` — сохраняется выражение, показывается результат.
- Счётчик проблем в шапке: «3 строки без цены, 1 конфликт» — клик фильтрует.
- Добавление строк: из каталога компонентов (поиск по 1000+ позиций прайса с автодополнением по категории) или свободная строка.
- Типовое место ручного ввода — цена трубы корпуса (договорная): строка «Труба СК/НПС-К 3000-0,1-10000» рождается красной, подсказка «указать стоимость трубы».

**Панель итогов** (всегда видна): Материалы · Труба/муфта · Формовка · Работы ФОТ · Прочие → **Себестоимость 11 603 440 ₽** → наценка [0,43] (редактируемая) → **Цена продажи 16 593 000 ₽** → рентабельность 30,1%. При тираже N≥2 — две колонки «за 1 корп. / за N корп.». Изменение любой строки анимированно обновляет итог — мгновенная обратная связь.

**Топбар:** статус (DRAFT/CALC/REVIEW/APPROVED), кнопки перехода по ролям, версия прайса, экспорт (КП, Заявка), снапшоты. Красные строки блокируют «На проверку» — состояние кнопки объясняет причину.

### 5.3 Гидравлический расчёт

Форма (расход, отметки, диаметры) + **график**: кривая системы и кривая насоса (паспортные точки — редактируемая мини-таблица), рабочая точка на пересечении подсвечена (Q=12,6 л/с, H=12,9 м). Кнопка «Применить насос к расчёту» → марка и параметры уходят в ОЛ и раздел «Оборудование».

### 5.4 Прайс-лист

Таблица ~1050 позиций: категория (14 значений, фильтр-чипы) · наименование · ЕИ · цена · поставщик · дата изменения. Inline-редактирование цены (BUYER). Версионирование: переключатель версий + diff-режим «что подорожало» (старая/новая цена, дельта %). Импорт из Excel с отчётом «обновлено/создано/пропущено».

### 5.5 Заявка на закупку

Read-only представление закупаемых строк расчёта: № · категория · наименование · ЕИ · кол-во · бюджетная цена · стоимость · дата закупки · отметка исполнения. Группировка по категориям, экспорт в Excel/PDF, печатная форма с реквизитами ООО «НТТ».

### 5.6 Каталог компонентов (TECHNOLOG, фаза 3)

Библиотека ~26 узлов с тегами (корпус / конструкции / системы / оборудование). Карточка узла: параметры, состав строк (тип МАТЕРИАЛ/ОПЕРАЦИЯ, формула по имени из реестра, k ФОТ), варианты, флаги. **Предпросмотр-материализация:** ввёл тестовые параметры (DN=2000, L=5000) — увидел готовые строки с ценами. Публикация «черновик → активен». Конструктор шаблона: дерево сборок drag-n-drop из каталога + биндинги параметров на поля ОЛ.

## 6. Статусная модель (виден каждому экрану)

```
DRAFT → CALC → REVIEW → APPROVED        REVIEW → CALC (возврат)
                                        любой → REJECTED (ADMIN)
```

APPROVED — расчёт заморожен (снапшот): вся таблица read-only, визуально «запечатан». Красные строки блокируют CALC→REVIEW.

## 7. Реальные данные для мокапов

Использовать в макетах реальную фактуру (из действующих расчётов):

- Изделие: «КНС 3000×11900 мм (подземная часть 11 600 мм), 25,13 л/с», заказчик АО «ГК «ЕКС», объект «ГКБ №52, ул. Пехотная, 3».
- Строки: «Труба СК/НПС-К 3000-0,1-10000» — 11,6 м — цена вручную; «Придание изделию товарного вида» — 26,8 чел.ч × 1207,8 ₽; «Механическое формованное дно» — 262,8 кг × 214,4 ₽; «Ламинирование дна к фальшполу» — 78,9 кг × 310,2 ₽; «ФОТ» — 73,6 чел.ч; «Задвижка чугунная клиновая DN150» — 5 шт; «Насос VSL.100.55.4.5.0D» — 3 шт; «Поплавковый выключатель, кабель 10 м» — 4 шт × 6000 ₽.
- Категории: Собственное производство, ФОТ, Метизы, Металлопрокат, Запорная арматура, Насосы/АТМ, Датчики, Шкафы…
- Итоги: себестоимость 11 603 440 ₽ → цена 16 593 000 ₽, наценка 0,43, рентабельность 30,07%.
- Наименования длинные («Фланец 50-10-01-1-В-12Х18Н10Т ГОСТ 33259-2015») — колонка наименования доминирует, обрезка с тултипом недопустима для печатных форм.

## 8. Визуальные требования

- Числа: разряды пробелами (11 603 440), рубли без копеек в итогах, 2 знака в ценах; моноширинные цифры (tabular-nums) во всех таблицах.
- Высокая плотность без клаустрофобии: строка таблицы ~32–36px, зебра или разделители на выбор дизайнера.
- Цветовой язык состояний (§5.2) — единственный обязательный цветовой контракт; остальная палитра свободна, но сдержанно-индустриальная (это инструмент завода, не маркетинг).
- Обе темы равноправны; проверка контраста WCAG AA в обеих.
- Язык интерфейса — русский; терминологию не «упрощать» (ОЛ, ФОТ, СН/PN/SN, чел.ч — профессиональный словарь пользователей).
- Иконография: минимальная, состояния важнее иконок.

## 9. Инвентарь UI-компонентов (для дизайн-системы)

Таблица-дерево с inline-редактированием · ячейка с двойным источником значения (расчёт/override) · панель итогов с live-обновлением · статус-бейдж и статус-переходы · счётчик/фильтр проблем · визард-форма с live-подсказками · график двух кривых с рабочей точкой · diff цен · чипы-фильтры категорий · модал (закрытие по фону отключаемо) · контекстное меню · переключатель темы · тосты/подтверждения · печатные формы (КП, Заявка).

## 10. Приоритеты и антицели

**Приоритеты:** 1) читаемость и скорость работы с таблицей 300+ строк; 2) мгновенная связь «правка → итог»; 3) прозрачность источника каждого числа (доверие — главная валюта против Excel); 4) работа в iframe Б24 без деградации.

**Антицели:** не делать «красивый дашборд с графиками» — это рабочий стол сметчика; не прятать данные за кликами (Excel-пользователи привыкли видеть всё); не изобретать собственную навигацию внутри вкладки Б24.

## 11. Ожидаемые артефакты дизайн-сессии

1. UI-kit: токены (цвета двух тем, типографика, отступы), состояния ячеек и строк из §5.2.
2. Мокапы: Калькулятор (основной кейс + все состояния строк + APPROVED read-only), Опросный лист (2–3 секции с live-подсказками), панель итогов с тиражом, Прайс с diff, Гидравлика с графиком, Dashboard.
3. Флоу: «от ОЛ до утверждения» и «закрыть красные строки».
4. Адаптация той же вёрстки под iframe Битрикс24 (1000px).

## 12. Что разошлось с реализацией (сверка 2026-09-08)

Разделы 1–11 не правились — ниже перечислено, где задание разошлось с построенной системой и что в коде на самом деле. Часть требований живёт только в README хендоффа (`design_handoff_ntt_calculator/README.md`), эта папка тоже не правится — такие пункты помечены.

**§2 Пользователи — ролей шесть, не пять.** Добавилась VIEWER (наблюдатель): `ntt-calculator/src/stores/auth.ts:4`, `backend/prisma/schema.prisma:17`, причём она же значение по умолчанию у нового пользователя (`schema.prisma:40`). Роль сделана под вкладку Битрикс24 — маршрут `/calculator` её пускает (`ntt-calculator/src/router/index.ts:63`), экран открывается только для просмотра (`views/CalculatorTreeView.vue:294`, `views/ProjectView.vue:170`), в топбаре плашка «👁 просмотр» (`CalculatorTreeView.vue:19`, `ProjectView.vue:41`), кнопки создания скрыты (`views/DashboardView.vue:25`). Ни бриф, ни хендофф этого поведения не описывают.

**§3 Контекст «iframe внутри Битрикс24» пока гипотетический.** В коде нет ни одного вызова BX24 API: resize вьюпорта, SSO и привязка сделки не написаны, приложение живёт только в standalone. Битрикс упоминается ровно четырьмя комментариями, и все они — про роль VIEWER под вкладку «Расчёт» (`ntt-calculator/src/router/index.ts:59`, `views/CalculatorTreeView.vue:291`, `backend/src/routes/estimates.routes.ts:35`, `backend/src/routes/projects.routes.ts:23`); больше от интеграции нет ничего. Она сама и её предусловие (домен + TLS) — в бэклоге, `ntt-calculator/doc/ROADMAP.md`, «Бэклог» п. 6. Два ограничения вёрстки из §3 при этом нарушены и всплывут при интеграции: главные экраны верстаются на всю высоту вьюпорта — `height: 100vh` у `.cw`, `.ol`, `.pr`, `.tpl`, `.app-layout` (`views/CalculatorTreeView.vue:632`, `views/SurveyKnsView.vue:518`, `views/PurchaseRequestView.vue:157`, `views/TemplatesView.vue:377`, `assets/main.css:157`), а боковая навигация не сворачивается — фиксированные 212px (`assets/main.css:161`).

**§4, §5.1 Опросный лист — не модал-визард, а отдельный полноэкранный экран.** В коде это самостоятельный маршрут `/survey/:id?` (`ntt-calculator/src/router/index.ts:47-51`, плюс редиректы старых адресов `:53-55`); «＋ Добавить единицу» в Проекте делает `router.push({ name: 'survey', … })` (`views/ProjectView.vue:39`, `:180`), модалов создания единицы там нет. Экран занимает весь вьюпорт (`views/SurveyView.vue:151`, `views/SurveyKnsView.vue:518` — `height: 100vh`). Пошагового визарда тоже нет: одна прокручиваемая форма и степпер секций сбоку, секции заполняются в любом порядке (`SurveyKnsView.vue:22-36`). Остальное §5.1 сделано — прогрессивное раскрытие, live-подсказки и рекомендованная `Нподз` (`engines/survey-kns.ts:100`), финальное превью перед материализацией (`SurveyKnsView.vue:255`, `:261`). Одна поправка к подписям из брифа: рядом с полями выводятся `Vэф`, `Vмин` и **`hраб`** (рабочая высота), а не `Vраб` (`SurveyKnsView.vue:376-378`). Расхождение намеренное и объяснено в коде — `hраб` считается от `Vмин`, а не от «Vраб» из ТЗ §5.6: только так воспроизводится контрольное число прототипа (`engines/survey-kns.ts:97-98`).

**§5.1 Переключатель ЕИ притока не конвертирует значение.** Сам переключатель есть (`views/SurveyKnsView.vue:165-174`: `v-model="form.rashod"` + `select` с л/с · м³/ч · м³/сут), но при смене единицы введённое число остаётся прежним: у `select` нет ни `@change`, ни watcher, а готовая `fromLps(lps, unit)` (`engines/survey-kns.ts:41`) вызывается только из тестов. Пользователь сам пересчитывает.

**§5.2 Топбар и §6 статусная модель — отменены (решение 2026-07-20).** Цепочки `DRAFT → CALC → REVIEW → APPROVED` в системе нет: сервер отвечает `422 STATUS_FLOW_REMOVED` на любой переход в REVIEW/APPROVED (`backend/src/routes/estimates.routes.ts:128-134`), разрешены только `DRAFT→CALC` и «любой → REJECTED (ADMIN)» (`:136-138`). Кнопки «На проверку» в интерфейсе не существует, `estimatesApi.patchStatus` (`ntt-calculator/src/api/estimates.ts:70`) не вызывается ниоткуда; статусы остались только подписью-бейджем (`views/CalculatorTreeView.vue:16`, `:369-373` — REVIEW/APPROVED «только у старых расчётов»). Точка фиксации перенесена на выпуск КП: гейт по строкам без цены стоит на `POST /api/estimates/:id/kp` (`estimates.routes.ts:305-310`, `code: ROWS_WITHOUT_PRICE`), он же снимает снапшот (`:315`). Отсюда два следствия для §5.2 и §6: красные строки блокируют не «На проверку», а «Сформировать КП» (`CalculatorTreeView.vue:34`, тултип ячейки — `components/calculator/CalcTableRow.vue:128`), а APPROVED-заморозка на сервере жива, но достаётся одним лишь старым расчётам: `PATCH /api/estimates/:id/survey` отвечает `422 ESTIMATE_FROZEN` (`estimates.routes.ts:509-515`), а через этот эндпоинт идёт и обычное сохранение из калькулятора (`stores/calcTree.ts:495`). Новые расчёты в APPROVED попасть уже не могут (`:128-134`), в интерфейсе заморозки нет вовсе (`readOnly` — это только VIEWER, `CalculatorTreeView.vue:294`), а обещанный в комментарии (`estimates.routes.ts:505-506`) возврат «Новая версия» не работает: перехода `APPROVED→CALC` в разрешённых нет (`:136-138`). После выпуска КП расчёт остаётся редактируемым, read-only даёт только роль VIEWER.

**§5.2, §9 Печатные формы: КП сделано, Заявка — нет.** КП выгружается с сервера: `GET /api/estimates/:id/kp/export?format=docx|pdf[&version=N]` (`backend/src/routes/estimates.routes.ts:355`), документ собирается из снапшота (`utils/kp-document.ts`, рендеры `utils/kp-docx.ts` и `utils/kp-pdf.ts`); нет снапшотов — `422 KP_NOT_ISSUED`. Образец заказчика («КПВ6393», 09.09.2026) подтвердил НДС **«в том числе»** (ставка 22%) и показал, что цены в нём стоят у каждой строки — но строки образца это узлы изделия, а не строки расчёта; цена узла требует разнести общие для изделия накладные, ПЗР, ацетон и СИЗ, а правило разнесения заводом не задано. Поэтому цена печатается там, где она точна, — **по позициям**: КП выпускается и на единицу (`GET /api/estimates/:id/kp/export`), и на проект целиком (`GET /api/projects/:id/kp/export?format=docx|pdf[&estimates=id,id]`, кнопка «КП на проект» на экране проекта), где позиция — единица оборудования (`utils/kp-document.ts`, `KpPosition`). В интерфейсе КП скачивается не из «экспорта» в топбаре, а из окна «Версии», по конкретной редакции (`views/CalculatorTreeView.vue:244`, `:250`, `:578`) — потому что расчёт после выпуска КП продолжает правиться. Заявка на закупку выгружается только в xlsx (`views/PurchaseRequestView.vue:12`, `:124-138`); PDF и печатной формы с реквизитами ООО «НТТ» нет.

**§5.2 Панель итогов: анимации обновления нет, тираж показан иначе.** Пересчёт живой (`views/CalculatorTreeView.vue:346`), но «вспышки» изменившейся суммы нет: себестоимость и цена продажи выводятся простыми интерполяциями (`:142-144`, `:151-153`), в стилях `.tot-cost`/`.tot-price` (`:716-719`) нет ни `animation`, ни `transition`, и во всём `ntt-calculator/src` нет ни одного `@keyframes`. Числится в бэклоге — `ntt-calculator/doc/ROADMAP.md`, «Бэклог» п. 7 («мелочи»). Тираж тоже сделан не двумя колонками «за 1 корп. / за N корп.»: главные цифры — за весь тираж (согласованы с таблицей, где количества умножены на N), а цена одного корпуса выводится отдельной строкой ниже (`CalculatorTreeView.vue:167-169`).

**§5.2 Корзина строки определяется единицей измерения, а не категорией.** Уточнение к тексту README хендоффа (`design_handoff_ntt_calculator/README.md:110`), где классификация описана по категориям. В коде `classifyRow` (`ntt-calculator/src/engines/economics.ts:105-110`) смотрит: явную метку `row.bucket` (её получают только труба и муфта корпуса) → `unit === 'чел. ч'` → «Работы, ФОТ» → `unit === 'кг'` → «Формовка» → иначе «Материалы на закупку» (константы — `engines/types.ts:55-56`). Категория в классификации не участвует вовсе; показательный случай — «Монтаж поплавковых выключателей»: категория «Собственное производство», ЕИ «чел. ч», идёт в труд. «Прочие затраты» вообще не класс строк, а вычисляемая сумма (ацетон + СИЗ + накладные, `economics.ts:229`).

**§5.3 Гидравлический расчёт: подэкрана и графика нет.** Реализована только счётная часть на сервере: `backend/src/routes/pump-station.routes.ts` — четыре POST (`/dimensions`, `/ring-stiffness`, `/discharge-pipe-diameter`, `/select-pump`, строки `32`, `55`, `80`, `106`), смонтирован как `/api/pump-station` (`backend/src/app.ts:53`); подбор диаметра напорного — `utils/pipe-hydraulics.ts`, подбор насоса по рабочей точке — `utils/pump-selection.ts` по каталогу из 61 модели Vandjord VSL (`prisma/seed-data/pumps.json`, модель `Pump` в `schema.prisma`). Кривых системы и насоса, рабочей точки на пересечении и отдельного экрана гидравлики в интерфейсе нет. Подбор при этом встроен прямо в опросный лист КНС (`ntt-calculator/src/composables/usePumpSelection.ts`): марка насоса и расчётный диаметр напорного показываются подсказками под соответствующими полями, марка кнопкой подставляется в поле и уходит в расчёт. Паспортные кривые насосов в системе есть (`PumpCurvePoint`, 559 точек у 56 моделей) и по ним идёт подбор, но кривую СИСТЕМЫ строить не из чего: геометрический напор и потери в сети опросный лист не спрашивает.

**§5.4 Прайс-лист: переключателя версий и diff нет.** *Обновление 10.09.2026:* импорт теперь двухшаговый — предпросмотр «что изменится» с процентом по каждой цене и повторами ключа, затем запись; появилась выгрузка в xlsx с листом «Проверка». Diff между версиями по-прежнему не показывается — только изменения загружаемого файла против текущего прайса. С того же дня список — одна таблица с прилипающей шапкой и сортировкой по наименованию, цене и дате; категории в боковой панели — фильтр на несколько сразу со счётчиками (считаются по остальным фильтрам), рядом с поиском — чипы «без цены» и «с замечаниями» (замечания считает сервер, `utils/price-issues.ts`); строки выводятся порциями по 200, фильтры живут в адресе страницы (`utils/price-registry.ts`). Есть таблица с поиском и фильтром категорий (список в боковой панели, а не чипы — `ntt-calculator/src/views/PricesView.vue:9-21`), inline-правка цены и поставщика для ADMIN/BUYER (`:125`, `:175`, `:250`) и импорт из xlsx с отчётом «создано / обновлено / пропущено» (`:40-52`, `:199`). Переключателя версий и diff-режима «что подорожало» в коде нет ни одного упоминания — при том что данные для них в БД копятся: каждый импорт заводит новую `PriceListVersion` (`backend/src/routes/prices.routes.ts:176-185`), а каждое изменение цены пишется в `PriceHistory` со старой и новой ценой — и при inline-правке (`prices.routes.ts:53`), и при импорте (`:164`; модель — `backend/prisma/schema.prisma:149-160`). Нет именно выдачи: ни эндпоинта, ни экрана. Наружу отдаётся только максимальная версия — `GET /api/refs/price-version` (`backend/src/routes/refs.routes.ts:47`), она и показывается в топбаре калькулятора (`stores/calcTree.ts:84`, `:89`).

**§5.5 Заявка на закупку: группировки по категориям нет.** Колонки совпадают с брифом целиком, включая пустые «Дата закупки» и «Отметка об исполнении» (`views/PurchaseRequestView.vue:29-45`), но строки идут плоским списком в порядке дерева (`:105-118`); экспорт — см. выше, только xlsx.

**§5.6 Каталог компонентов: вместо него «Шаблоны», этап 1.** Экран `/templates` для TECHNOLOG существует (`ntt-calculator/src/router/index.ts:82-86`, `views/TemplatesView.vue`), но это редактор четырёх справочников — нормы патрубков, веса труб GRP, матрица корпуса, эллиптические днища (`TemplatesView.vue:186-191`). Карточки узла с составом строк, предпросмотра-материализации («ввёл DN=2000, L=5000 — увидел строки с ценами»), публикации «черновик → активен» и drag-n-drop конструктора шаблона нет; структура разделов и узлов по-прежнему в коде (`engines/template-kns.ts`, `engines/template-emk-kol.ts`), в БД только данные. Второй этап — в бэклоге, `ntt-calculator/doc/ROADMAP.md`, «Бэклог» п. 5.

**§8 Live-группировки разрядов при вводе нет.** Требование из README хендоффа (`design_handoff_ntt_calculator/README.md:94`): «980000 → 980 000» прямо по мере набора. В коде ячейки количества и цены связаны как `:value` + `@change` без `@input`, директивы или маски (`components/calculator/CalcTableRow.vue:18`, `:22`, `:35`, `:40`), поэтому во время набора поле показывает сырой текст, а разряды появляются после применения ввода (blur/Enter), когда пересчитывается `qtyText` (`:117-118`). Вместо маски сделана компенсация на входе: `stripDigitGrouping` вырезает пробелы-разделители из выражения перед вычислением (`engines/expr.ts:167`), так что вставленное «980 000» разбирается корректно. Форматирование самих значений выполняется: разряды пробелами через `toLocaleString('ru-RU')` и `tabular-nums` глобально (`assets/main.css:150`). У ячеек калькулятора это локальный `fmt` в `components/calculator/CalcTableRow.vue:111-112`, а общий `engines/format.ts` они не используют — он подключён только на карточках и в прайсе (`views/PricesView.vue:168`, `views/ProjectView.vue:162`, `components/dashboard/EstimateCard.vue:33`, `components/dashboard/ProjectCard.vue:42`).
