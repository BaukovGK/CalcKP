## 1. Концепция

Инженер отвечает на вопросы опросного листа — система сама собирает полную спецификацию изделия с ценами и трудозатратами. Дальше инженер не «считает смету», а **тюнингует заготовку**: включает/выключает блоки, правит отдельные количества и цены. Система мгновенно пересчитывает итог и показывает цену продажи.

Ключевое ощущение: *«я управляю изделием, а не таблицей»*. Excel-предок требовал знать, какие ячейки трогать можно, а какие нельзя; здесь запрещённых ячеек нет — есть параметры, расчётные значения и явные ручки-переопределения.

**Антицель:** свободный табличный редактор, где каждый расчёт строится с нуля. Проверено реверсом: 6 реальных смет = один каркас + точечные правки.

## 2. Роли

Роли БД — `Role` (`backend/prisma/schema.prisma:11-17`).

| Роль | Что делает в механике | Мотивация |
|---|---|---|
| ENGINEER | Заполняет ОЛ, тюнингует расчёт, выпускает КП | Быстро получить корректную смету |
| MANAGER | Видит и правит чужие расчёты, следит за маржой. Согласование через статусы отменено (§10) | Уверенность, что маржа не потеряна |
| BUYER/ADMIN | Ведёт прайс НН | Актуальные цены = честный итог |
| TECHNOLOG | Правит справочники материализации на экране «Шаблоны» | Нормы соответствуют производству |
| VIEWER | Только просмотр расчёта — вкладка «Расчёт» в Битрикс24 | Видеть цифру, не имея прав её менять |
| Система | Считает всё, что можно посчитать | — |

## 3. Core loop

```
 ┌─────────────────────────────────────────────────────────┐
 │ 1. ОПРОСНЫЙ ЛИСТ                                        │
 │    выбрал тип изделия → заполнил параметры и флаги      │
 └────────────────┬────────────────────────────────────────┘
                  ▼  «Создать расчёт» (материализация шаблона)
 ┌─────────────────────────────────────────────────────────┐
 │ 2. РАСЧЁТ (заготовка)                                   │
 │    разделы созданы, количества посчитаны, цены          │
 │    подтянуты, ФОТ-спутники добавлены                    │
 └────────────────┬────────────────────────────────────────┘
                  ▼  цикл тюнинга (основной геймплей)
 ┌─────────────────────────────────────────────────────────┐
 │ 3. ТЮНИНГ                                               │
 │    вкл/выкл раздел · добавить/удалить строку ·          │
 │    override количества · override цены ·                │
 │    закрыть «красные» строки (нет цены)                  │
 │        └── каждое действие → мгновенный пересчёт итога  │
 └────────────────┬────────────────────────────────────────┘
                  ▼
 ┌─────────────────────────────────────────────────────────┐
 │ 4. ИТОГ: себестоимость → наценка → цена продажи         │
 │    → DRAFT → CALC · выпуск КП = снапшот (§10)           │
 │      → выгрузки: КП docx/pdf, Заявка на закупку         │
 └─────────────────────────────────────────────────────────┘
```

Петля второго порядка: изменение параметра ОЛ *после* создания расчёта → дерево сразу материализуется заново и сохраняется (ОЛ — основной экран изделия, §8.4), расчётные количества обновляются сами, а ручные overrides переносятся и, если легли на изменившееся расчётное, вспыхивают конфликтом, который дожидается экрана расчёта (§8.3).

## 5. Механика строки (атом системы)

Каждая строка — конечный автомат с двумя независимыми каналами: **количество** и **цена**.

### 5.1 Канал количества

```
qtyCalc  ──(формула шаблона от ОЛ и справочников)──►  read-only, серый
qtyManual ──(ввод инженера)────────────────────────►  приоритет, синий
qty = qtyManual ?? qtyCalc
     × флаг раздела (выкл → 0)
     × кол-во корпусов (тираж)
```

Правила:
- `qtyCalc` никогда не редактируется и никогда не теряется: сброс override возвращает расчётное значение (кнопка «↺ к расчётному»).
- Ввод `qtyManual` разрешает произвольные арифметические выражения (`1.55*2+2.88*2`) — в Excel так считают длины; выражение сохраняется, отображается результат.
- **Текст в числовые поля не попадает** — ни в расчёте, ни в ОЛ (`ntt-calculator/src/utils/numeric-input.ts`, ставится на документ в `main.ts`). В поле с классом `num` или атрибутом `data-numeric` печатаются только символы грамматики выражений: цифры, `,` `.`, пробел-разделитель разрядов, `+ − * /`, скобки, `=` в начале. Буква с клавиатуры не вставляется; из вставки лишнее вычищается, цифры остаются. Если значение и после этого не разбирается («2**3»), поле подсвечивается красным с подсказкой, а ОЛ не сохраняется, пока его не исправят («не сохранено: исправьте поля, выделенные красным»). Раньше такой ввод молча становился «пусто»: цена трубы пропадала из расчёта, а инженер видел в поле свой текст.
- Строка без формулы (добавленная вручную) имеет только `qtyManual`.

### 5.2 Канал цены

```
priceCatalog ──(поиск в прайсе по ключу C+N+U)──►  read-only, серый
priceManual  ──(ввод инженера)──────────────────►  приоритет, синий
price = priceManual ?? priceCatalog
sum   = qty × price
```

Правила:
- Промах по прайсу (`priceCatalog = null`) и нет `priceManual` → строка **красная**, сумма = 0, счётчик «незакрытых» строк в шапке. Типовой случай — труба/муфта корпуса: цена всегда договорная, вводится вручную.
- Ключ C+N+U сравнивается **в каноническом виде** (с 10.09.2026): одиночные пробелы, без пробелов по краям, кириллица на месте латинских двойников («ГOCT» → «ГОСТ», «108x8» → «108х8», «M12-7H» → «М12-7Н»). Правила — `backend/src/utils/price-name.ts`, копия во фронтенде — `engines/price-name.ts`, общие примеры — `price-name.vectors.json`. Их применяют импорт прайса, миграция `20260910120000_normalize_price_names` (привела 111 уже сохранённых наименований), поиск цены в расчёте и сопоставление строк при пересборке: невидимая разница больше не делает строку «красной» и не теряет ручные правки.
- Прайс ведётся выгрузкой и загрузкой листа «НН» (экран «Реестр цен»). Выгрузка — книга в раскладке листа мастер-шаблона плюс «Поставщик» и лист «Проверка» (позиции без цены и с подозрительными ценами: цена не сходится с ценой без скидки, лист за штуку расходится с ценой за м² больше чем на 40 %). Загрузка — в два шага: предпросмотр (новые позиции, изменения цен с процентом, повторы ключа с обеими ценами, пустые цены, исправленные наименования) и только потом запись. Позиции, которых нет в файле, не удаляются; **пустая цена в файле цену базы не стирает**; поставщик читается, если в файле есть его колонка. Правила — `backend/src/utils/price-import.ts`; консольный вариант — `node dist/tools/import-prices.js <книга.xlsx> [--dry-run]`.
- Материализация **фиксирует** применённую цену: `priceCatalog` пишется один раз, при вставке узла (`ntt-calculator/src/engines/template-kns.ts:197-198`), и хранится в дереве вместе с номером версии прайса (`CalcTree.priceListVersion`). Активную версию сервера отдаёт `GET /api/refs/price-version` (MAX по `PriceListVersion`, `backend/src/routes/refs.routes.ts:47`); топбар показывает версию, из которой построен расчёт.
- `priceManual` при повторной материализации (правка ОЛ) переносится в новое дерево и не трогается — `ntt-calculator/src/stores/calcTree.ts:292`.
- ⚠️ **не реализовано:** пересчёт `priceCatalog` по новой версии прайса и подсветка дельты (было/стало у каталожной цены). Обновление прайса меняет **строчные** цены только у новых расчётов; чтобы старый расчёт увидел новые каталожные цены, его дерево пришлось бы рематериализовать, а такого действия нет. Оговорка: на четыре ставки экономики (ФОТ, накладные, ацетон, СИЗ) это не распространяется — они в дереве не фиксируются и подхватываются старым расчётом сразу (§9, §12.3).

### 5.3 Классификация

- `category` — из фиксированного списка 16 категорий. Категория определяет флаг «Закупка»: категории «Собственное производство», «Работы», «ФОТ» — не закупка, остальные 13 — закупка (попадают в Заявку).
- `unit` определяет физический смысл: `кг` — формовка/ламинат (масса участвует в расчёте ФОТ и ацетона), `чел. ч` — труд (участвует в накладных), прочие — штучные материалы.
- Наименование трубы корпуса генерируется: `Труба {материал}-К {DN}-{PN_ОЛ}-{SN}`. У КНС и КОЛ материал всегда `СК/НПС` (`ntt-calculator/src/engines/survey-kns.ts:215-222`, `ntt-calculator/src/engines/template-emk-kol.ts:427`); у ЕМК он зависит от типа среды — `СК/ВЭС` для химстойкой, иначе `СК/НПС` (`ntt-calculator/src/engines/survey-emk-kol.ts:27-29`, `ntt-calculator/src/engines/template-emk-kol.ts:276-277`). В марку идёт **обозначение** жёсткости: по ТТ МВК заказчик видит 8000/12000 вместо расчётных 5000/10000 (`snDesignation`, §7.2).
- При смене параметров ОЛ дерево рематериализуется, и наименование вместе с ключом прайса перегенерируется: `load()` сравнивает `surveyRev` с `treeSurveyRev` и строит свежее дерево, перенося в него ручные правки (`ntt-calculator/src/stores/calcTree.ts:143-161`).
- Гильза патрубка отдельной штучной строкой **не** генерируется: в прайсе это масса — строка «Формовка гильз» в кг, диаметр гильзы уходит в пояснение (`ntt-calculator/src/engines/template-kns.ts:340-349`). ⚠️ **не реализовано:** наименование вида `Стеклокомпозитная гильза Ø{D}`.

## 6. Механика ФОТ-спутников

К каждой производственной операции (строка «Собственное производство» с ЕИ=кг) система автоматически прикрепляет строку-спутник «ФОТ»:

```
трудоёмкость (чел.ч) = ROUNDUP( масса_операции_кг × k , 0.1 )

k = 0.28  если наименование операции содержит «мех»    (механическая формовка)
k = 0.56  если содержит «ламин»                        (ламинирование)
k = 1.0   иначе                                        (ручная формовка и особые случаи)
```

- Спутник реагирует на итоговое `qty` родителя (после override), не на `qtyCalc`; тираж к спутнику не применяется — он уже пришёл из массы родителя (`recalcFotSatellites`, `ntt-calculator/src/engines/fot.ts:59-78`).
- Цена спутника = позиция прайса «ФОТ / ФОТ / чел. ч» (актуальная ставка 1207,8 ₽) — фиксируется при материализации (`operationWithFot`, `ntt-calculator/src/engines/template-kns.ts:208-228`).
- Спутник можно переопределить вручную (H-канал), но нельзя удалить отдельно от родителя.
- Отдельные строки узлов каталога задают коэффициент явно (особые ламинирования с k=1.0) — коэффициент хранится в строке узла, эвристика по подстроке — значение по умолчанию.

## 7. Механика разделов

### 7.1 Каркас KNS (эталон, порядок фиксирован)

Каркас — `KNS_SECTIONS` (`ntt-calculator/src/engines/template-kns.ts:155-163`); в скобках — узлы, которые материализуются из ОЛ сегодня:

1. Корпус (A1 обечайка + товарный вид, A2 днище формованное + ламинирование, A5 патрубки с гильзами, A9 теплоизоляция)
2. Лестница (B1)
3. Перекрытие, площадка, несущие балки (B2 перекрытие, B6 анкерное крепление против всплытия)
4. Вентиляционный стояк (C1)
5. Напорный трубопровод (C2) ← самый «живой»: 55–109 строк в реальных файлах, из ОЛ выводятся только направляющие насосов, остальное инженер добавляет из каталога
6. Крепёж (C3)
7. Оборудование и запорная арматура (C4 запорная арматура, D1 насосная группа)

EMK — 8 разделов (`EMK_SECTIONS`, `ntt-calculator/src/engines/template-emk-kol.ts:53-62`): + автогабариты из объёма, эллиптические днища у горизонтальной, шахта обслуживания, отдельный раздел 2 «Корзина». KOL — 7 разделов (`KOL_SECTIONS`, там же :64-72): без насосов и напорного трубопровода, + горловина, тоже с разделом 2 «Корзина». Общие узлы (лестница, перекрытие, вентстояк, крепёж) переиспользуются из шаблона КНС.

### 7.2 Триггеры включения (флаг ← поле ОЛ)

| Блок | Триггер | Поведение |
|---|---|---|
| Теплоизоляция | ОЛ «теплоизоляция» + глубина ТИ | Узел A9 материализуется с `enabled = флаг ОЛ`; выкл → qty всех строк блока = 0 (`ntt-calculator/src/engines/template-kns.ts:363-372`) |
| Корзина сороудерживающая | ОЛ «дробилка/корзина» = «корзина» или «обе» | Узел D3 (`ntt-calculator/src/engines/basket-grinder.ts`, `buildBasket`): у КНС — в разделе 1 «Корпус», у ЕМК и КОЛ — отдельный раздел 2. Состав по эталону: уголок 10 м, перфолист 2 м², труба направляющих ROUNDUP(2·H/1000), цепь ROUNDUP(H/1000 + 1), где H — глубина лотка подводящего; такелаж у КНС — кольца и скобы, у ЕМК и КОЛ — пруток «Круг 5 мм» и карабин на 2 м цепи; работы 6 + 5 чел.ч при DN < 2500, 7 + 6 — при большем, направляющие 2 + 2. У КНС при корзине вместе с дробилкой труба направляющих корзины = 0 (лист КНС, строка 105). Без глубины лотка строки цепи и направляющих остаются пустыми с примечанием |
| Дробилка | ОЛ «дробилка/корзина» = «дробилка» или «обе» | Узел D4 (`buildGrinder`), только КНС и КОЛ — в разделе 1: формовка канала 4,7 м² × 7 мм × 1850 кг/м³ (ФОТ 0,28), ламинирование площадки × 3/10 (ФОТ **1**), уголок направляющих ROUNDUP(2·H/1000), цепь 5 мм, подвес; у КНС ещё труба рамы ROUNDUP(2·DА/1000), кольца и «Монтаж направляющих дробилки» 2 чел.ч. Сам измельчитель (ПОТОК П-200…П-800) эталон не материализует — подбирается по притоку и добавляется в «Оборудование». В листе ёмкости узла дробилки нет, у ЕМК тумблер на расчёт не влияет |
| Задвижка на подводящем | ОЛ «арматура на подводящем» | Кол-во задвижек = подводящих × флаг: `gateValveCount` (`ntt-calculator/src/engines/survey-kns.ts:247-249`), строка в узле C4 |
| Горловина (KOL) | ОЛ «горловина» + d,h | Входит в полную глубину корпуса и в длину лестницы; крышка горловины — узел A8 (`computeKolGeometry`, `ntt-calculator/src/engines/survey-emk-kol.ts:148-160`; `neckCoverMassKg`, там же :167-170; `ntt-calculator/src/engines/template-emk-kol.ts:492`) |

| Марка трубы по ТТ МВК | ОЛ «По ТТ МВК» | Меняет **обозначение** жёсткости в наименовании: 5000 → 8000, 10000 → 12000 (`snDesignation`, `ntt-calculator/src/engines/survey-kns.ts:161,171-173`). Вес и трудоёмкость считаются по расчётной жёсткости — изделие то же |
| ⚠️ **не реализовано:** Фальшпол | флаг раздела | Признака фальшпола нет ни в форме ОЛ (`KnsSurveyForm`), ни в параметрах материализации (`KnsSurveyParams`). Днище КНС всегда одно: «Механическое формованное дно» + «Ламинирование дна к фальшполу» (`ntt-calculator/src/engines/template-kns.ts:277-300`); альтернативы «плоское днище» нет. Развилка «эллиптические ↔ плоское» есть только у ЕМК и зависит от размещения, а не от фальшпола |
| ⚠️ **не реализовано:** Лестница нерж ↔ алюминиевая | выбор в разделе | Единственный вариант — «Лестница нержавеющая» (`ntt-calculator/src/engines/template-kns.ts:417-418`) |
| ⚠️ **не реализовано:** Крышка стеклокомпозит ↔ металл | выбор в разделе | Развилки нет; формовка горловины ничем не обнуляется |
| ⚠️ **не реализовано:** МВК-комплект | ОЛ «По ТТ МВК» | Флаг доходит до шаблона (`ntt-calculator/src/stores/calcTree.ts:232`), но влияет только на обозначение SN в марке трубы. Строк «поручень», «откидные люки», «перехватывающее устройство» в движке нет; вентиляция одна и безусловная — «Вентиляционный стояк ПЭ Ду110» (`ntt-calculator/src/engines/template-kns.ts:520-521`). Экран ОЛ при этом показывает блок «МВК-комплект» (`ntt-calculator/src/views/SurveyKnsView.vue:393`) |
| ⚠️ **не реализовано:** Датчики / расходомер / ШУ | ОЛ, по-элементно | Категории есть (`Датчики`, `Расходомеры`, `Шкафы` — `ntt-calculator/src/engines/types.ts:33-35`), строк нет: состав зависит от гидравлики и каталога АШУ, добавляется вручную |
| ⚠️ **не реализовано:** АТМ, запасные насосы | ОЛ «запасных» | Строки автоматической трубной муфты (АТМ) нет ни в одном шаблоне; `surveyToParams` переносит из ОЛ только `nRab` и `nRez` (`ntt-calculator/src/stores/calcTree.ts:237-238`) — поля `nZap` в `KnsSurveyParams` нет |

Выключенный раздел не удаляется: `toggleSection`/`toggleComponent` меняют только флаг `enabled`, `qtyManual`/`priceManual` сохраняются, обнуление количества — вычисление: флаг раздела и компонента сворачивается в предикат по строке (`sectionEnabledFor`, `ntt-calculator/src/engines/template-kns.ts:775`), а само обнуление делает `resolveQty` (`ntt-calculator/src/engines/row.ts:34`). Включение обратно восстанавливает всё, включая overrides.

Но **видимы такие строки не по умолчанию**: фильтр таблицы убирает их вместе с подзаголовком компонента, пока не включён чекбокс «выключенные» (`ntt-calculator/src/views/CalculatorTreeView.vue:54` и :418, инициализация `ghosts: false` — :341). Свёрнутого «призрачного» состояния как отдельного режима отображения нет.

## 8. Механика пересчёта (reactivity)

### 8.1 Граф зависимостей

```
ОЛ-параметр ──► qtyCalc строк ──► qty ──► масса/часы ──► ФОТ-спутники
                                   │                        │
Прайс ──► priceCatalog ──► price ──┴──► sum ──► подытоги раздела
                                                  │
                                     итоговый блок (§9) ──► цена продажи
```

Любое изменение распространяется вниз синхронно, за один тик; итог всегда консистентен.

### 8.2 Что на что влияет (примеры)

- DN корпуса → вес трубы (справочник DN;PN;SN), масса днища (`bottomMassKg`), перекрытия (`topSlabMassKg`), теплоизоляции (`insulation`), наименование трубы, чел.ч «товарного вида» (`marketableAppearanceHours`, DN/1300) — `ntt-calculator/src/engines/formulas.ts:66,86,105,135`. ⚠️ **не реализовано:** тип петель (DN<2000 — простые) — строк петель в движке нет.
- Глубина L → длина трубы, теплоизоляция, лестница (`ladder`), направляющие (`pumpGuidesM`), анкеры (`anchorCount`) — `ntt-calculator/src/engines/formulas.ts:233,250,260`.
- DN патрубка → диаметр гильзы `CEILING(DN+100; 50|100)` (`sleeveDiameter`), нормы формовки патрубка (`NozzleNorm`), прорезка отверстия 0,5 чел.ч/м окружности (`cutoutHours`, `ntt-calculator/src/engines/formulas.ts:223`), норма болтов фланцевого соединения.
- Расход/напор → гидравлика → рекомендация насоса. Работает сквозь весь поток: опросный лист по притоку, расчётному напору и числу рабочих насосов спрашивает `POST /api/pump-station/select-pump` (`composables/usePumpSelection.ts`), подобранная марка уходит в `derived.pumpModel`, оттуда в параметры материализации и в наименование строки раздела 7 — «Насос {марка}», а дальше в спецификацию КП. Отбор идёт по паспортной кривой с окном запаса по напору 0,5…2,0 м: запас страхует не рост притока (он уже в требуемом напоре), а несовпадение реального насоса с паспортом. По умолчанию подставляется наименьший достаточный, но экран даёт список всех подходящих моделей с их рабочими точками — инженер выбирает другую, включая отсечённые по минимальному запасу (они показаны отдельной группой). Поле «Марка насосов» в ОЛ — ручное переопределение подбора по общему правилу «расчёт + override» (§5.1). Цена насоса остаётся договорной: в прайсе НН категория «Насосы, АТМ» пуста, поэтому строка по-прежнему «красная». Диаметр напорного трубопровода (`POST /api/pump-station/discharge-pipe-diameter`) показывается подсказкой и в поле DN автоматически не подставляется: от DN зависят наименования строк, и молчаливая правка увела бы за собой ручные цены при рематериализации (§8.3).

### 8.3 Конфликт «ОЛ изменился после тюнинга»

Правило: **расчётные значения обновляются всегда, ручные — никогда молча**. Дерево материализуется заново, overrides переносятся (`reconcileTrees`, `ntt-calculator/src/stores/calcTree.ts`). Строка, где `qtyManual` перекрывает изменившееся расчётное значение, получает `qtyCalcPrev` — расчётное «было» — и попадает в `conflictIds`; инженер решает по каждой: «Оставить моё» (`keepOverride`) или «Принять новое» (`dropOverride`), оба гасят `qtyCalcPrev`.

`qtyCalcPrev` хранится **в дереве**, а не в памяти экрана: пересчёт теперь запускает сам ОЛ (§8.4), и конфликт, рождённый там, иначе не дожил бы до экрана расчёта. При двух правках ОЛ подряд запоминается самое раннее неразрешённое значение — инженер видит то, поверх чего ставил свою цифру.

**Узлы, которые включает тумблер ОЛ** (теплоизоляция, фланцевый патрубок под задвижку, аварийный трубопровод, корзина, дробилка), помнят ответ ОЛ в `enabledCalc` (`CalcComponent`, `engines/template-kns.ts`). Правило переноса — выигрывает последняя правка: сменился тумблер в ОЛ — узел берёт состояние из ОЛ; не менялся — остаётся, как его переключил инженер в расчёте (`reconciledEnabled`, `stores/calcTree.ts`). До 10.09.2026 состояние узла переносилось из старого дерева всегда, и выключенная в ОЛ теплоизоляция продолжала считаться. У деревьев, собранных раньше, прежний ответ ОЛ неизвестен — считается, что узел в расчёте не переключали.

### 8.4 ОЛ — основной экран изделия (с 2026-09-10)

Единица проекта открывается **опросным листом**, а не расчётом (`ProjectView.vue`, `openUnit`); в расчёт ведут «расчёт →» на карточке и «Открыть расчёт →» в ОЛ. Каждая правка ОЛ после паузы в вводе (`SYNC_DELAY_MS` = 700 мс) пересобирает и сохраняет расчёт одним запросом — ОЛ, дерево и итоги (`composables/useSurveySync.ts` → `applySurvey` стора). Кнопки «Сохранить ОЛ» больше нет; в шапке ОЛ — настоящий статус («сохранено 10:42 · расчёт пересчитан»), в живой панели — цена продажи.

- Нагрузка сверяется с сохранённой (`stableStringify` — jsonb хранит ключи в своём порядке): одинаковая — запроса нет. Без этого лист пересобирал расчёт при каждом открытии: марка насоса приходит от подбора асинхронно, и её появление выглядело правкой.
- Запросы не перекрываются: правка во время сохранения ставит следующее в очередь.
- «Создать расчёт» строит расчёт сразу и оставляет пользователя в ОЛ — уже как листе изделия (`/survey/:id`).
- Справочники и прайс кешируются на время работы с листом (`ensureContext`); экран расчёта при открытии берёт их свежими.

### 8.5 Цены, связанные с полями ОЛ

Цена трубы корпуса (₽/м.п., все три изделия), цена насоса (₽/шт, КНС) и цена трубы шахты ёмкости или горловины колодца (₽/м.п., связь `servicePipePrice` — диаметр у них свой, и цена корпуса к ним не подходит) вводятся в ОЛ и живут в расчёте ручной ценой своих строк. Строки помечены `priceBinding` (`engines/types.ts`); связь двусторонняя:

- ОЛ → расчёт: материализация кладёт поле в `priceManual`, при переносе правок цена связанной строки из старого дерева **не** переносится — ОЛ здесь источник;
- расчёт → ОЛ: правка такой цены в расчёте при сохранении пишется обратно в форму (`boundPricesPatch`), иначе следующая правка ОЛ вернула бы старую цифру.

Сегменты «трубы частями» — та же труба, связаны с тем же полем. Цены, введённые в расчёте до появления полей, при открытии ОЛ переезжают в пустые поля (`engines/price-binding.ts`, `boundPricesFromTree` — по пометке либо по приметам старых деревьев: труба шахты или горловины — строка трубы узла A8).

**Цены насосов — позиции прайса**: «Насосы, АТМ | Насос <марка> | шт», по одной на каждую из 61 модели каталога (`backend/prisma/seed.ts`, `seedPumpPrices`). Заводятся пустыми — цены у производителя в каталоге нет, их вносит закупка на экране прайса. Поле ОЛ «Цена насоса» перекрывает прайс; плейсхолдер показывает цену марки из прайса.

⚠️ **не реализовано:** массовое действие «сбросить все конфликты». В сторе есть только поштучные `keepOverride`/`dropOverride`, в UI — кнопки внутри одной строки (`ntt-calculator/src/components/calculator/CalcTableRow.vue:53-54`). Кнопка «сбросить ✕» в панели фильтров чистит фильтры, а не конфликты.

## 9. Механика итогов (экономика)

Пайплайн поверх суммы строк, единый для всех изделий:

```
часы_фитингов = Σ чел.ч работ без «изготов» в наименовании
часы_РМУ      = Σ чел.ч работ с «изготов»
масса_формовки = Σ qty строк с ЕИ=кг

ПЗР        = ROUNDUP(часы_фитингов / 11, 0.1) × ставка_ФОТ
Ацетон     = ROUNDUP(масса_формовки × 0.05, 0.1) × цена_ацетона
СИЗ и РМ   = ROUNDUP(часы_фитингов + 302) × цена_СИЗ       ← ЕИ «ед.», НЕ ПЗР (см. ниже)
Накладные  = ROUNDUP(часы_фитингов + ПЗР, 0.1) × ставка_накладных   ← 1584.73 ₽/чел.ч

Себестоимость (с НДС) = Материалы_закупка + Труба_муфта + Формовка
                      + Работы_ФОТ(вкл. ПЗР) + Прочие(Ацетон+СИЗ+Накладные)

Цена продажи   = ROUNDUP( Себестоимость × (1 + наценка), до 100 ₽ )   ← наценка 0.43
Рентабельность = (Цена − Себестоимость) / Цена                        ← справочно ≈ 30%
```

> **Уточнение по первоисточнику (2026-07-16).** Формулы сверены с `Шаблон 3.0.xlsx`, лист «Калькулятор КНС»:
> - ПЗР `J443 = ROUNDUP(часы/11; 0,1)` ✓, ацетон `J445 = ROUNDUP(масса×0,05; 0,1)` ✓, накладные `J447 = ROUNDUP(J441+J443; 0,1)` ✓ — совпадают.
> - **СИЗ `J446 = ROUNDUP(J441+302,)` — расходится с прежней редакцией.** ПЗР в формуле не участвует; `302` — константа шаблона, ЕИ «ед.». Реализуется как в эталоне; **❓ смысл константы 302 требует уточнения у завода**.
> - **ПЗР входит в корзину «Работы, ФОТ»** (`N453 = N441+N443+N442`), а **не** в «Прочие» (`N455 = ацетон+СИЗ+накладные`).
> - Себестоимость `N449 = N454+N451+N452+N455+N453` — ровно 5 корзин.

- Наценка — редактируемое поле расчёта (`ntt-calculator/src/views/CalculatorTreeView.vue:147-148`), сохраняется в `totals.markup` и поднимается при загрузке. Рентабельность считается тут же и видна в реальном времени. **По умолчанию — константа движка** `DEFAULT_MARKUP = 0.43` (`ntt-calculator/src/engines/economics.ts:59`): ⚠️ **не реализовано** взятие значения по умолчанию из настроек — подсистемы настроек в системе нет (см. §13).
- Ставки (ФОТ, накладные, ацетон, СИЗ) — позиции прайса, а не константы кода: обновление прайса меняет экономику **всех** расчётов, в том числе старых. В отличие от строчных цен, ставки в дереве не фиксируются: `rates` пересобираются из живого прайса при каждом `load()` (`ntt-calculator/src/stores/calcTree.ts:108-113`), в `save()` уходят только `costRub`, `salePriceRub`, `markup`, `tirage` (`…calcTree.ts:493-507`), и ниоткуда больше `rates` не восстанавливаются. Значит открытие старого расчёта после правки прайса пересчитывает ПЗР, накладные, ацетон и СИЗ по новым ставкам; замораживает цифру только снапшот (§10). Ключи — `ФОТ|ФОТ|чел. ч`, `ФОТ|Накладные расходы|чел. ч`, `Прочие материалы|Ацетон|кг`, `Прочие материалы|СИЗ и РМ|ед.`; при промахе по ключу подставляется `FALLBACK_RATES` (`ntt-calculator/src/stores/calcTree.ts:38-43`).
- НДС отдельно не выделяется — цены прайса с НДС (правило предметной области). Печатная форма КП выделяет его «в том числе» справочной строкой, не начисляя сверху; ставка 22% — по образцу заказчика (`backend/src/utils/kp-document.ts`).

### 9.1 Тираж

Поле «Кол-во корпусов» — целое ≥ 1 (валидация `ntt-calculator/src/views/CalculatorTreeView.vue:500-505`); все количества строк домножаются на N (`ntt-calculator/src/engines/row.ts:44`).

Итоговый блок показывает **одну** колонку — за весь тираж. При N ≥ 2 к ней добавляется одна строка «за 1 корп.» с ценой продажи одного корпуса (`ntt-calculator/src/views/CalculatorTreeView.vue:167-169`): её нельзя получить делением итога на N, потому что ПЗР, СИЗ и округления нелинейны, — стор считает её отдельным прогоном экономики с `tirage = 1` (`economicsUnit`, `ntt-calculator/src/stores/calcTree.ts:350-358`).

⚠️ **не реализовано:** две колонки «за 1 корп.» / «за N корп.» со всеми составляющими. Себестоимость, корзины и рентабельность в пересчёте на один корпус в UI не выводятся, хотя `economicsUnit` вычисляет их целиком.

## 10. Прогрессия статусов и точка фиксации

> **Переписано 2026-07-16 по уточнению заказчика.** Прежняя редакция описывала
> согласование внутри калькулятора (CALC → REVIEW → APPROVED, «APPROVED
> замораживает расчёт»). Это **не соответствует реальному процессу**.

Реальный процесс:

```
Предварительный расчёт → КП → согласование КП в коммерческом отделе
   │                                    (вне калькулятора)
   │                                          │
   ▼                                          ▼
снапшот при выпуске КП            дальнейшая проработка инженером:
(что именно ушло заказчику)       трубы, оборудование, насосы, детали
                                            │
                                            ▼
                        сметы, спецификации, списки для ERP, закупка
                                     (не проработано)
```

**Расчёт не замораживается.** Инженер правит его *после* выпуска КП — это
следующий шаг процесса, а не нарушение. Требование «APPROVED замораживает
расчёт, редактирование блокируется» отменено.

**Снапшот привязан к выпуску КП, а не к статусу.** Он фиксирует, из каких цен
и какой версии прайса родилась цифра в согласуемом документе: прайс меняется,
и без снапшота подписанную цифру через месяц не восстановить. Расчёт при этом
живёт дальше — снапшоты и есть механизм версионирования (§4).

**У снапшота есть причина** (`EstimateSnapshot.reason`, `backend/src/utils/snapshot-reason.ts`):

| Причина | Когда снимается | КП печатается | Мешает удалить единицу |
|---|---|---|---|
| `CREATE` | при создании единицы изделия — временной слепок исходного состояния | нет | нет |
| `MANUAL` | ручная фиксация в окне «Версии» | да | да |
| `KP` | выпуск КП, после проверки строк без цены | да | да |

Слепок создания нужен потому, что ОЛ пересобирает расчёт при каждой правке
(§8.4): без него то, с чего единица начала, не восстановить. Он снимается один
раз — после первой сборки расчёта, повтор возвращает уже снятый. КП по нему не
печатается (422 `KP_NOT_PRINTABLE`): проверку строк без цены он не проходил, и
документ занизил бы итог «красными» строками. По той же причине он не делает
единицу «готовой» для КП на проект и не мешает её удалить — иначе
неудаляемой стала бы каждая новая единица. Снапшоты, снятые до появления
причины, получили `KP` — так они и работали.

**Красные строки (нет цены) блокируют выпуск КП.** Их сумма равна нулю, то
есть такая строка молча занижает итог; в документ заказчику это попасть не
должно. Типовой случай — труба корпуса: цена договорная (§5.2). Гейт стоит в
`POST /api/estimates/:id/kp` — 422 `ROWS_WITHOUT_PRICE`
(`backend/src/routes/estimates.routes.ts:305-313`), там же снимается снапшот.

**Печатная форма КП строится из снапшота**, а не из текущего состояния:
`GET /api/estimates/:id/kp/export?format=docx|pdf[&version=N]`
(`backend/src/routes/estimates.routes.ts:355`). Без снапшотов — 422
`KP_NOT_ISSUED`: печатать нечего. Кнопки `docx`/`pdf` живут в окне «Версии»
калькулятора (`ntt-calculator/src/views/CalculatorTreeView.vue:242-251`),
каждая выгрузка пишется в аудит как `estimate.kp.export`.

**КП выпускается на единицу и на проект целиком.**
`GET /api/projects/:id/kp/export?format=docx|pdf[&estimates=id,id]`
(`backend/src/routes/projects.routes.ts`) собирает документ из последних
снапшотов единиц проекта: по позиции на единицу, у каждой своя спецификация,
своя редакция и своя цена, общая сумма — их сложение. Единица без снапшота
не выбрасывается молча, а даёт 422 `KP_UNITS_NOT_ISSUED` с её именем;
`estimates` ограничивает состав, если КП нужно на часть проекта. Модель
документа одна на оба случая (`utils/kp-document.ts`, `KpPosition`):
КП на единицу — документ из одной позиции. Аудит — `project.kp.export`.

**Работы и ФОТ в КП не печатаются** (`utils/estimate-tree.ts`, `isWorkRow`):
заказчик покупает изделие, а не трудозатраты. Операции собственного
производства («Ламинирование частей корпуса 112 кг», «Прорезка отверстия
0,7 чел. ч») и их спутники ФОТ занимали три четверти строк спецификации: в КНС
из 58 строк осталось 23. На цену это не влияет — она берётся из снапшота, куда
работы входят через себестоимость. Из гейта «строки без цены» работы не
исключаются: там они занижают сумму по-настоящему.

⚠️ Следствие: раздел, в котором нет ни одной закупаемой позиции, из документа
пропадает целиком — так исчезла «Лестница» (в ней только изготовление и
монтаж). Это ограничение построчной спецификации; лечится переходом на
узловую, где позиция документа — узел изделия («Лестница, 1 компл.»), как в
образце заказчика. См. `Вопросы_заводу.md` §8.

**Количества в КП — на весь тираж**, как и цена продажи: состав и сумма в
одном документе обязаны относиться к одному заказу, поэтому число изделий
печатается в подписи позиции.

**Количество, заданное выражением, считает фронт.** `qtyManual` хранит
выражение (§5.1), парсер живёт только в `engines/expr.ts`; заводить второй на
сервере — значит рассинхронизировать грамматику. Поэтому при сохранении в
каждую строку дерева кладётся `qtyResolved` — результат за одно изделие
(`ntt-calculator/src/stores/calcTree.ts`, `treeForSave`), и бэкенд читает его,
а не разбирает выражение (`backend/src/utils/estimate-tree.ts`,
`resolveRowQty`). Если результата нет (снапшот снят до появления поля),
количество считается НЕОПРЕДЕЛЁННЫМ, а не нулевым: строка без цены блокирует
выпуск КП, а печать отказывает с 422 `KP_SPEC_INCOMPLETE` — выдуманное число в
документе заказчику хуже отказа.

**Статусы в Фазе 1:** используются `DRAFT` и `CALC`; `DRAFT → CALC` происходит
при первом сохранении расчёта. Переход в `REVIEW`/`APPROVED` **запрещён** —
`PATCH /api/estimates/:id/status` отвечает 422 `STATUS_FLOW_REMOVED`
(`backend/src/routes/estimates.routes.ts:125-131`); единственные разрешённые
переходы — `DRAFT → CALC` (ENGINEER/MANAGER/ADMIN) и `→ REJECTED` (ADMIN).
`REVIEW`/`APPROVED` остаются в enum БД (`backend/prisma/schema.prisma:26-32`)
ради старых расчётов, и их русские подписи рендерятся в UI, чтобы такой
расчёт не выглядел сломанным (`ntt-calculator/src/views/CalculatorTreeView.vue:371`,
`ntt-calculator/src/views/ProjectView.vue:252`). От legacy-`APPROVED` осталась
заморозка: правка ОЛ такого расчёта отдаёт 422 `ESTIMATE_FROZEN`
(`backend/src/routes/estimates.routes.ts:505-512`), а удаление запрещено.

## 12. Инварианты и антиправила

1. Сумма итогового блока всегда равна сумме включённых строк + начисления §9 (в Excel это контролировалось дублирующей формулой — здесь инвариант движка, покрывается тестами).
2. Ручной ввод никогда не перезаписывается системой без подтверждения.
3. Формулы живут в реестре функций (`ntt-calculator/src/engines/formulas.ts`), состав узлов — в шаблоне. Вставка узла в расчёт — **материализация**: копия состава с зафиксированными расчётными значениями, применёнными ценами и коэффициентами. Дерево самодостаточно **по строкам**: изменения шаблона и каталожных цен влияют только на новые вставки. Исключение — четыре ставки экономики (§9): в дереве они не хранятся, а пересобираются из живого прайса при каждом `load()`, поэтому ПЗР, накладные, ацетон и СИЗ старого расчёта пересчитаются по новым ставкам при следующем открытии. Точка фиксации документа — **снапшот при выпуске КП**, а не статус (§10): снапшот создаётся в `POST /:id/kp` и вручную в `POST /:id/snapshot`; обработчик смены статуса снапшотов не снимает, а переход в `APPROVED` запрещён.
4. Ключ прайса — тройка (категория, наименование, ЕИ); символ `~` в наименованиях запрещён (наследие VLOOKUP). Валидация стоит на импорте прайса: строка с `~` пропускается с причиной (`backend/src/utils/nn-sheet.ts:103-106`).
5. Удаление строки шаблона запрещено — только выключение; удалять можно только строки, добавленные вручную (`removeRow` ищет строку с флагом `isCustom`, `ntt-calculator/src/stores/calcTree.ts:476-484`).
6. Балансные константы (см. §13) не хардкодятся по строкам, а задаются один раз — именованными экспортами в `formulas.ts`, `fot.ts`, `economics.ts`, `rounding.ts`.
