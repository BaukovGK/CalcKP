## 2. Ключевая находка: `ntt-calculator/doc/Шаблон 3.0.xlsx`

**Это тот самый мастер-шаблон** (2,3 МБ), описанный в `Реверс_калькуляторов.md` §2. Все 19 листов на месте. Соответствие имя→файл проверено через `xl/_rels/workbook.xml.rels`, а не по порядку:

| Лист | rId → файл | Размер | Содержимое |
|---|---|---|---|
| `НН` | rId18 → sheet18.xml | **709 КБ** | Прайс, ~1044 позиции |
| `Калькулятор КНС` | rId11 → sheet11.xml | **453 КБ** | Эталонная спецификация, 452 строки |
| `Вес трубы, ПЭ трубы` | rId17 → sheet17.xml | **151 КБ** | 162 строки GRP + 26 ПЭ |
| `Для расчетов` | rId16 → sheet16.xml | **105 КБ** | Инженерные матрицы |
| `Справка по подбору АШУ Омега` | rId19 → sheet19.xml | 62 КБ | ~220 шкафов |
| `Вспомогат. таблицы` | rId13 → sheet13.xml | 4,6 КБ | BOM монтажных петель |

**Следствия — план меняется в лучшую сторону:**

1. Справочники (веса труб, инженерные матрицы, АШУ, прайс) **извлекаются программно**, а не набиваются руками. Снимается главный риск этапа 3 и источник опечаток.
2. `sheet11.xml` содержит **формулы ячеек**, а не только значения. Шаблон КНС выводится **из первоисточника**, а не реконструируется из прозы. Это принципиально: проза §4.3 Реверса даёт ~10 формул из нескольких сотен.
3. Появляется **эталон формул**. ⚠️ **Важное ограничение (уточнено 2026-07-16):** `Шаблон 3.0.xlsx` — это *шаблон*, а **не** файл ОЛ3487. Его цена продажи — 8 229 200 ₽, часы фитингов — 649. Контрольные числа задачи (620,3 чел.ч → 16 593 000 ₽) взяты из файла ОЛ3487, **которого у нас нет**. Шаблон даёт: (а) точные формулы, (б) собственный самосогласованный кейс для тестов (наценка 0,43; рентабельность 30,07% — сходится). Построчной сверки с ОЛ3487 не будет — тесты §2 опираются на 5 чисел задачи, как и было задумано.

**Оговорка:** в книге есть `externalLinks` (7 шт.) — часть значений может быть ссылками на внешние файлы. Проверяется на этапе 1; если критичные данные окажутся внешними ссылками, потребуются исходные файлы.

### 4.1-ter. ✅ ПРИНЦИП: прототип диктует только внешний вид, данные — из ТЗ

**Решение заказчика 2026-07-16 (действует для всех сверок с хендоффом):**

> Прототип диктует только внешний вид панелей. Все данные валидны из ТЗ.

Правило применения:

| Что берём из прототипа | Что берём из ТЗ / справочников |
|---|---|
| компоновка, ширины зон, сетки, типографика | домены полей (списки значений) |
| формулировки подписей и подсказок | наличие и смысл полей и флагов |
| порядок элементов, состояния, поведение | формулы и константы |
| токены цвета, отступы, размеры | наименования и категории (только из прайса НН) |

**Расхождения, разрешённые этим принципом** (обнаружены при сверке ОЛ 2026-07-16):

| Поле | ТЗ §5.6 — **взято** | Прототип — отклонено |
|---|---|---|
| Тип НС | 4: Канализационная / Ливневая / Дренажная / **Водопроводная** | 3 (без Водопроводной) |
| Материал патрубка | ПЭ / ПВХ / ПНД / ПП / **Асбестцемент** / **Корсис** / стеклокомпозит | ПЭ / ПВХ / ПНД / ПП / «сталь» / стеклокомпозит |
| Флаг «арматура на подводящем» | есть: `задвижки = кол-во подводящих × флаг` | флага нет |
| Список DN | **справочник весов: 30 значений** (300…500 шаг 50, 600…3000 шаг 100) | 9 значений — укороченный мок |

Тот же принцип уже применялся в калькуляторе: README приводил «Изофом ППЭ ОР 15 1,5х40 — 890 ₽», а в прайсе НН позиция называется «**Теплоизоляция -** Изофом ППЭ ОР 15 1,5х40» и стоит **750 ₽**. Взят прайс: числа README — данные мок-прототипа.

**Практическое следствие:** мок-списки прототипа брать нельзя в принципе. На DN это уже стреляло — в укороченном списке нет DN 3000, то есть кейса приёмки №2.

### Этап 4-bis. КП и точка фиксации — НОВОЕ (уточнение заказчика 2026-07-16) — ✅ ВЫПОЛНЕНО (API 2026-07-16, печатная форма 2026-09-08)

**Причина.** Подтверждение расчёта внутри калькулятора не требуется: согласование идёт над печатной формой КП, в коммерческом отделе, мимо системы. Реальный процесс:

```
Предварительный расчёт → КП → согласование КП в коммерческом отделе (вне системы)
   → дальнейшая проработка инженером (трубы, оборудование, насосы, детали)
   → сметы, спецификации, списки для ERP, закупка        ← не проработано
```

**Что это меняет:**

| Было (ТЗ/Механика) | Стало |
|---|---|
| Согласование внутри: CALC → REVIEW → APPROVED | Согласование **вне системы**, над печатным КП |
| APPROVED **замораживает** расчёт | **Заморозки нет**: инженер правит расчёт *после* КП — это следующий шаг процесса |
| Снапшот при APPROVED | Снапшот **при выпуске КП** — фиксирует, что ушло заказчику |
| Красные строки блокируют CALC → REVIEW | Красные строки **блокируют выпуск КП** |
| Статусы — часть цели задачи | Фаза 1: только `DRAFT`/`CALC`; REVIEW/APPROVED/REJECTED остаются в API и enum, но UI их не назначает — только отображает у старых расчётов |
