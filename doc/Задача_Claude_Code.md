# Задача для Claude Code: сборка и развёртывание «НТТ Калькулятор» по ТЗ

Скопировать этот файл как стартовый промт сессии Claude Code, запущенной в корне репозитория `web/сметы`.

## Контекст

Ты дорабатываешь существующий проект до рабочего продукта и разворачиваешь его. Прочитай перед началом (в этом порядке):

1. `doc/ТЗ.md` — **ТЗ v1.4, главный нормативный документ** (архитектура, БД, API, роли, §9 модель расчёта, §10 Битрикс24, §7 TODO)
2. `doc/Механика_калькулятора.md` — поведение калькулятора (состояния строк, реактивность, экономика, таблица баланса)
3. `doc/Библиотека_компонентов.md` — метамодель узла каталога, принятые упрощения (§6), модель данных (§4)
4. `doc/Реверс_калькуляторов.md` — первоисточник формул (фактология, не редактировать)
5. `design_handoff_ntt_calculator/README.md` — дизайн-токены (Archivo, радиус 0, палитры тёмной/светлой тем), hi-fi прототипы `*.dc.html` — эталон вида и поведения экранов ОЛ и Калькулятора

Кодовая база: `backend/` (Express 5 + Prisma 7 + PostgreSQL 16, частично реализован по §4 ТЗ) и `ntt-calculator/` (Vue 3 + Pinia + Vite, частично реализован по §5). Инвентаризуй фактическое состояние кода относительно ТЗ прежде чем писать новое — ТЗ описывает и сделанное, и целевое.

Окружение: Windows, установлены Node 24, PostgreSQL 16 (пользователь `postgres`, порт 5432). Претензий к обратной совместимости нет — данных в системе ещё нет.

## Цель

Фаза 1 по ТЗ: работающий продукт «ОЛ → материализованный расчёт → тюнинг → итог → статусы → заявка на закупку», задеплоенный локально одной командой. Битрикс24 (§10), редактор каталога (TECHNOLOG UI) и гидравлический график — НЕ в этой задаче.

## Этапы

### 1. БД и Prisma
- Актуализировать `schema.prisma` по §3 ТЗ v1.4: `PriceItem` с ключом (category, name, unit) + поля priceBase/discount/currency/comment; роль `TECHNOLOG` в enum Role; `Estimate.surveyData` хранит параметры ОЛ + дерево расчёта (Json).
- Миграции + сид: admin/manager/engineer из seed.ts.

### 2. Движок расчёта (`ntt-calculator/src/engines/`)
Реализовать по §9 ТЗ и диздоку, чистыми функциями с unit-тестами (Vitest):
- Строки МАТЕРИАЛ/ОПЕРАЦИЯ/ФОТ; двухканальный override (qtyCalc/qtyManual с арифметическими выражениями, priceCatalog/priceManual); строка «без цены» = сумма 0.
- ФОТ-спутники: `чел.ч = ROUNDUP(масса × k, 0.1)`, k = 0.28 (`*мех*`) / 0.56 (`*ламин*`) / 1.0.
- Экономический блок: часы фитингов/РМУ (по `*изготов*`), масса формовки (ЕИ=кг), ПЗР = ROUNDUP(часы/11, 0.1) × ставка ФОТ, ацетон = ROUNDUP(масса×0.05, 0.1) × цена, СИЗ = ROUNDUP(часы+ПЗР) × цена, накладные = (часы+ПЗР) × ставка, себестоимость из 5 корзин, цена = ROUNDUP(себест × (1+наценка), до 100 ₽), рентабельность.
- **Контрольные числа для тестов** (реальный расчёт ОЛ3487): при часах фитингов 620.3 → ПЗР 56.4 чел.ч; накладные (620.3+56.4) × 1584.73 = 1 072 387 ₽; себестоимость 11 603 440 → цена 16 593 000, рентабельность 30.07%. Ставки: ФОТ 1207.8, накладные 1584.73, ацетон 109.4, СИЗ 122, наценка 0.43.

### 3. Шаблон КНС и материализация
- Шаблон изделия КНС (= ЛНС/ДНС) как конфигурация: 7 сборок-разделов (§9.1 ТЗ), состав строк и формулы количеств — из `Реверс_калькуляторов.md` §4 (реализовать как минимум: корпус-труба с весом из справочника, товарный вид DN/1300, днище по формуле масс, патрубки с гильзами CEILING(DN+100), теплоизоляция, ФОТ-спутники; остальные разделы — каркас с ручными строками).
- Справочник весов GRP-труб (DN;PN;SN → кг/пм): оцифровать из реверса как сид-таблицу + `GET /api/refs/pipe-weights`.
- «Создать расчёт» из ОЛ = материализация: копия строк с зафиксированными значениями в `surveyData` (Json-дерево, §6.2–6.3 Библиотеки). Флаги ОЛ управляют включением сборок.
- ОЛ КНС по §5.6 ТЗ, включая авторасчёты: Нподз (формула в §5.6), SN по глубине с override, арматура по формулам — поведение и вид по прототипу `Опросный лист v2.dc.html`.

### 4. Бэкенд-доделки (TODO §7 ТЗ)
- `POST /api/prices/import` — импорт xlsx (SheetJS), upsert по (category,name,unit), PriceHistory, ответ {updated,created,skipped}.
- `POST /api/estimates/:id/snapshot` + `GET .../snapshots`; автоснапшот при APPROVED.
- `GET /api/refs/nomenclature` из БД.
- Запись AuditLog: estimate.create, estimate.status_change, prices.update, prices.import, user.create.
- Блокировка перехода CALC→REVIEW при строках без цены (валидация на бэке).

### 5. Фронтенд
- Калькулятор по прототипу `Калькулятор v2.dc.html`: дерево сборок с тумблерами и scrollspy, таблица с шестью состояниями ячеек, фильтры проблем, панель итогов с наценкой/тиражом, статус-бар. Токены из README хендоффа (обе темы).
- Заявка на закупку: view закупаемых строк + экспорт xlsx.
- Прайс: таблица, inline-редактирование, импорт.

### 6. Развёртывание
- `docker-compose.yml`: postgres:16 + backend + nginx (отдаёт собранный фронт, проксирует /api). Для запуска без Docker — `verify.ps1` по образцу: сборка фронта и бэка, prisma migrate deploy, сид, smoke-проверка /api.
- `.env.example` для обоих приложений. README с командами запуска.

## Критерии приёмки

1. Unit-тесты движка зелёные, включая контрольные числа из §2.
2. Сценарий целиком руками: создать проект → единицу КНС с ОЛ (данные ОЛ3487: DN3000, приток 25.13 л/с, 2+1 насоса) → расчёт материализован, Нподз = 11 600 → ввести цену трубы вручную → красных строк нет → CALC → REVIEW → APPROVED создаёт снапшот → заявка на закупку выгружается.
3. Импорт прайса из xlsx работает и пишет PriceHistory.
4. `docker compose up` (или verify-скрипт) поднимает всё с нуля.
5. `tsc`/`vue-tsc` и линт без ошибок.

## Правила

- Не менять `doc/Реверс_калькуляторов.md`. Расхождение кода с ТЗ — сначала спросить, потом менять ТЗ.
- Формулы — в коде (реестр функций), не в данных; DSL не вводить (§6.4 Библиотеки).
- Числа: tabular-nums, разряды пробелами; терминологию не упрощать.
- Коммиты по этапам; после каждого этапа — работающее состояние.
