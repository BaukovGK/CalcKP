# Библиотека компонентов расчёта

**Документ:** декомпозиция калькуляторов КНС/ЕМК/КОЛ на переиспользуемые компоненты — первичные «кубики», из которых собираются существующие шаблоны и формируются новые расчёты.
**Связанные документы:** `Механика_калькулятора.md` (движок строки, ФОТ-спутники, реактивность), `Реверс_калькуляторов.md` (первоисточник формул), `ТЗ.md` §9.
**Реализация:** реестр формул — `ntt-calculator/src/engines/formulas.ts`; узлы каталога материализуют шаблоны `ntt-calculator/src/engines/template-kns.ts` и `template-emk-kol.ts` (что именно материализуется сегодня — §2.1).
**Основание:** реверс 6 реальных файлов показал, что три калькулятора собраны из одних и тех же узлов с побайтово совпадающими формулами (днище, патрубки, петли, теплоизоляция и т.д.). Раздел Excel — не атом: атом — **компонент** (узел изделия).

## 1. Метамодель: универсальный узел каталога, флаги, рекурсивные сборки

### 1.1 Универсальный компонент

Один тип компонента на всю систему. Свойства — три аспекта стоимости, но с разным статусом:

```
Узел каталога (NodeDef) — единая сущность: компонент = узел-лист, сборка = узел с детьми
├── id, code, название, тег (рубрика каталога), флаги (см. 1.2)
├── Параметры (schema): вход; связываются с полями ОЛ или вводятся вручную
├── Варианты (mutually exclusive исполнения: нерж/алюм, ПЭ/нерж…)
├── Состав — строки двух типов и/или дочерние узлы (рекурсия — сборки из сборок):
│   ├── МАТЕРИАЛ   закупаемая позиция: категория, наименование, ЕИ, формула qty (formulaRef)
│   └── ОПЕРАЦИЯ   собственное производство: масса/объём (formulaRef), ставка ₽/кг,
│                   коэффициент k_ФОТ  →  порождает ФОТ
└── Выходы (агрегаты): Материалы ₽ · Работа ₽ · ФОТ чел.ч/₽ · масса формовки кг
```

**ФОТ — не третий список строк, а производная операций:** `чел.ч = ROUNDUP(масса × k, 0.1)`, k = 0.28 (мех) / 0.56 (ламинирование) / 1.0 (ручная), ставка — из прайса. Ручной override возможен, независимый ввод — нет. Основание: во всех 6 реальных файлах ФОТ вычисляется от массы операции; независимый ФОТ создаёт двойной ввод и рассинхронизацию.

**Тип «Операция» — гибрид работы и материала:** строка формовки одновременно материал (кг ламината, цена ₽/кг) и источник труда (ФОТ). Жёсткая дихотомия Работа/Материал не покрывает 105 позиций «Собственное производство» — поэтому в модели не два свойства-«ведра», а два типа строк, один из которых порождает третий аспект.

**Универсальна оболочка, не содержимое:** компонент без схемы параметров и формул — статичный BOM, новые расчёты выродятся в копипасту чисел. Формулы количеств от параметров (DN, L, SN…) — обязательная часть определения; ссылаются только на собственные параметры и справочники.

### 1.2 Флаги-ограничения (вместо классов)

Ограничения узла задаются тремя флагами; типовые «классы» — их комбинации:

| Флаг | Действие |
|---|---|
| `hasOperations` | Узел содержит операции: порождает ФОТ и массу формовки; участвует в итогах «Формовка» и разделении фитинги/РМУ |
| `purchasable` | Строки узла попадают в Заявку на закупку (выводится из категорий состава) |
| `lockedComposition` | Состав задан BOM-справочником, построчно не редактируется (петли A10, крепёж C3) |

Комбинации: производственный узел (A1–A10, B2, B3) = `hasOperations`; закупочный узел (C4, D1–D5) = `purchasable` без операций (кроме строк «монтаж» — чел.ч напрямую); монтажный набор = `purchasable + lockedComposition`; чистые работы (прорезка, подготовка трубы) = без обоих.

В коде фазы 1 флагов нет — нет и `NodeDef` (§5). Фактически работает только `purchasable`, и выводится он ровно так, как здесь описано, — из категории строки: закупочными считаются все категории, кроме «Собственное производство», «Работы» и «ФОТ» (`ntt-calculator/src/engines/types.ts:48`, `row.ts:19`).

### 1.3 Иерархия сборки — рекурсивная

```
Строка ⊂ Компонент ⊂ Сборка ⊂ … ⊂ Расчёт изделия ⊂ Заказ (комплекс)
```

- **Сборка** — именованная группа: может содержать строки, компоненты и вложенные сборки. Разделы шаблона («Корпус», «Оборудование») — это сборки верхнего уровня. Глубина не фиксируется схемой (ограничение — в UI, 3–4 уровня).
- Фиксированная трёхуровневая лестница «компонент→сборка→комплекс» отвергнута: одиночные строки (ацетон) не образуют сборку, а заказ из нескольких изделий (реальный случай — файл ОЛ3246: КНС + колодец в одном заказе) требует уровня выше. Рекурсия покрывает оба случая без искусственных обёрток.
- Сборка любого уровня сохраняется в каталог и переиспользуется (типовая обвязка нитки, типовой МВК-комплект).

### 1.4 Правила сборки (не выражаются внутри компонента)

Слой правил на уровне сборки/расчёта:

1. **Взаимоисключение** (корзина ↔ дробилка) — правило сборки, а не свойство компонента.
2. **Мета-флаги** (МВК включает строки в четырёх разных узлах) — правило расчёта, транслируемое в варианты нескольких компонентов.
3. **Биндинги параметров** (глубина L → и обечайка, и лестница, и направляющие) — задаются на уровне шаблона/сборки.
4. **Экономический хвост** (ПЗР, ацетон, СИЗ, накладные, наценка) — глобальный пайплайн над всеми строками расчёта; компонентом не является и в иерархию не входит.

### 1.5 Прочие правила

1. Компонент вставляется в расчёт многократно (патрубки, нитки) — каждый экземпляр со своими параметрами.
2. Overrides (qtyManual/priceManual) живут в экземпляре, не в определении.
3. Определения компонентов и сборок версионируются; расчёт хранит ссылку на версию.

**Шаблон изделия** = сборка верхнего уровня с биндингами параметров на поля ОЛ. **Новый расчёт нестандартного изделия** = сборка компонентов вручную — цель декомпозиции.

Ни один шаблон не материализует **A4, A6, A7, A10, B3, B4, B5, B7, D2, D4, D5**. Это не отказ от узлов, а граница опросного листа: материализуется то, что из ОЛ выводится, остальное инженер добавляет строками в расчёт (template-kns.ts:732).

Материализованные узлы, у которых часть проектного состава пока не строится:

- **A1** — только труба и «придание товарного вида». Подготовка трубы в реестре есть (`pipePrepHours`, formulas.ts:73), но не вызывается ни одним шаблоном; исполнение «частями» и стыковка сегментов в шаблоне отсутствуют.
- **B2** — формовка перекрытия, ламинирование и прорезка одного типового люка Ø800. Крышка люка, рама, петли/замки строк не дают; «рама 6–7 чел.ч (порог DN 2500)» не реализована нигде. Вычитание массы люков формула умеет — `topSlabMassKg(dn, hatchMassKg, hatchCount)` (formulas.ts:105, тест formulas.test.ts:96), но шаблон вызывает её как `topSlabMassKg(s.dn)` (template-kns.ts:445): кол-во люков в ОЛ не задаётся (комментарий template-kns.ts:478).
- **A3 и A8 (шахта ЕМК)** — массы формовки берутся из матрицы «Для расчетов», в шаблон она не выведена: строки рождаются с пустым количеством и заполняются вручную (template-emk-kol.ts:317, :374).
- **C2** — только изготовление и монтаж направляющих насосов, причём как ТРУД (чел.ч = длина × 0,25), а не метраж материала. Расхождение с каталогом: направляющие числятся в составе **D1**, а материализуются здесь, в C2 (`buildPressurePipe`, template-kns.ts:554-595; формула `pumpGuidesM`, formulas.ts:233). Отводы, тройники и фланцы нитки добавляются вручную (комментарий template-kns.ts:567).
- **C4, D1** — количества считаются, а конкретную позицию прайса (задвижка под нужный DN, марка насоса) выбирает инженер: строка рождается «красной» намеренно (комментарии template-kns.ts:658 и :693).

## 3. Сборка изделий из компонентов

Существующие шаблоны выражаются через каталог полностью (○ — узел, который шаблон ещё не материализует, §2.1):

| Раздел шаблона | КНС/ЛНС/ДНС | ЕМК | Колодец |
|---|---|---|---|
| 1. Корпус | A1 A2 A4○ A5×n A6○ A7○ A9 A10○ (+D3○\|D4○) | A1 (A2\|A3) A4○ A5×n A9 A10○ B3○ (+A8 при шахте) | A1 A2 A4○ A5×n A8 A9 A10○ |
| 2. Лестница | B1 | B1 | B1 |
| 3. Перекрытие, площадка | B2 B3○ B4○ B5○ B6 D5○ (B7-элементы○) | B2 B5○ B6 | B2 B5○ B6 |
| 4. Вентстояк | C1 | C1 | C1 |
| 5. Напорный трубопровод | C2×n_ниток | C2×n (при насосах) | — |
| 6. Крепёж | C3 | C3 | C3 |
| 7. Оборудование | C4 D1 D2○ D5○ | C4○ D1○ D2○ (D3\|D4○) | C4○ |

Нумерация в таблице — по КНС; каркасы разделов у трёх изделий разные и заданы в коде: КНС 7 разделов (`KNS_SECTIONS`, template-kns.ts:156), ЕМК 8 — корзина отдельным разделом 2, лестница 3, перекрытие 4, напорный 6, оборудование 8 (`EMK_SECTIONS`, template-emk-kol.ts:53), колодец 7 — как ЕМК, но без напорного трубопровода (`KOL_SECTIONS`, template-emk-kol.ts:64). Поэтому корзина D3 у ЕМК и колодца сидит не в «Корпусе» и не в «Оборудовании», а в собственном разделе, а разделы «Оборудование» у ЕМК и колодца шаблон оставляет пустым каркасом (template-emk-kol.ts:578, :603).

Экономический итог (ПЗР, ацетон, СИЗ, накладные, наценка) — **не компонент**: глобальный пайплайн над всеми строками расчёта (`Механика_калькулятора.md` §9).

**Сценарий «новый расчёт из компонентов»** (целевой для нестандартных изделий — усреднительные резервуары, КНС с нестандартной обвязкой, камеры переключения):

1. Создать расчёт «с нуля» или из копии ближайшего шаблона.
2. Добавлять компоненты из каталога в нужные разделы; у каждого экземпляра заполнить параметры (или связать с полем ОЛ).
3. Движок генерирует строки, ФОТ-спутники и цены; дальше — обычный тюнинг (overrides).
4. Собранную конфигурацию можно **сохранить как новый шаблон изделия** (ADMIN/ENGINEER+подтверждение) — библиотека растёт от практики.

## 4. Следствия для модели данных (дополнение к ТЗ §3)

Модель после принятых упрощений (§6):

| Сущность | Поля |
|---|---|
| `NodeDef` (каталог, единая сущность для компонентов и сборок) | id, code (A1…D5, …), name, **tag** (рубрика каталога: корпус/конструкции/системы/оборудование — свойство для группировки, без логики), **флаги** `hasOperations` / `purchasable` / `lockedComposition` (§1.2), paramsSchema (Json), variants (Json), состав (Json): строки {тип МАТЕРИАЛ/ОПЕРАЦИЯ, категория, генератор наименования, ЕИ, **formulaRef** — имя функции из реестра, k_ФОТ} и ссылки на дочерние `NodeDef` (рекурсия — сборки из сборок), правила сборки (взаимоисключения, мета-флаги, биндинги), **version** (int, инкремент при изменении — для аудита каталога) |
| `Estimate.surveyData` (Json-документ) | Параметры ОЛ + дерево расчёта: **материализованные** копии узлов на момент вставки (`nodeCode` справочно, params, enabled, строки с зафиксированными qtyCalc, применённым k_ФОТ, applied-ценой) + overrides + свободные строки. Реляционных узлов дерева нет (`backend/prisma/schema.prisma:79`) |
| Реестр формул | TypeScript-модуль в коде — `ntt-calculator/src/engines/formulas.ts`: именованные функции (`pipeMassKg(L, кг/пм)`, `bottomMassKg(DN)`, `topSlabMassKg(DN, m_люка, n)`, `lookupNozzleNorm(нормы, DN)`, `anchorCount(Дн, H)`, `ladder(H)`…). Новая формула = релиз; новый компонент из существующих формул = запись в каталоге без релиза |

Из полей `NodeDef` в коде есть только `code` — как справочный `nodeCode` материализованного компонента (§2.1); самой сущности каталога в схеме нет (фаза 2 не начата, §5), поэтому и `version` узла пока не существует.

**Трассируемость цены** (требование предметной области — цены и ставки ФОТ меняются часто, формулы редко): каждая строка расчёта фиксирует применённые на момент расчёта цену, ставку ФОТ и коэффициент k; расчёт хранит `priceListVersion`; изменения прайса пишутся в `PriceHistory`. Пиннинг версий определений не нужен — материализация делает расчёт самодостаточным, версия `NodeDef` служит аудиту состава.

Строки состава ссылаются на формулы по имени (`formulaRef`) из реестра функций в коде — DSL/evaluator в модели отсутствует (упрощение §6.4). Исключение — ручные overrides количеств в расчёте: допускаются простые арифметические выражения (`1.55*2+2.88*2`), вычисляемые безопасным парсером арифметики без функций (`ntt-calculator/src/engines/expr.ts`: рекурсивный спуск, без переменных, функций и степени; `eval` не используется).

## 5. Порядок внедрения

1. **Фаза 1 — сделана:** движок строк + жёсткие шаблоны (разделы как сейчас в Excel) — компоненты неявные, зашиты в код шаблона (`engines/row.ts`, `fot.ts`, `economics.ts`, `template-kns.ts`, `template-emk-kol.ts`; состав материализации — §2.1).
2. **Фаза 2 — не начата:** выделение компонентов A1–D5 в конфигурацию (`NodeDef`), шаблоны пересобираются на узлах каталога — поведение не меняется, появляется каталог. Каталог правит разработчик (конфигурация). Модели `NodeDef` в `backend/prisma/schema.prisma` нет.
3. **Фаза 3 — частично:** роль `TECHNOLOG` и редактор данных шаблонов есть (§6.2), UI сборки нестандартного расчёта из каталога и «сохранить как шаблон» — нет. В калькуляторе пункт «Компонент из каталога…» открывает поиск по **прайсу** и добавляет одиночную строку, а не узел каталога (`ntt-calculator/src/views/CalculatorTreeView.vue:527`).

Такой порядок позволяет запуститься с проверенными шаблонами и постепенно раскрыть конструктор без переписывания движка.

## 6. Принятые упрощения модели (зафиксированы)

1. **Компонент и сборка — одна сущность** `NodeDef`; «компонент» — узел-лист, сборки собираются из сборок рекурсивно без ограничения схемой.
2. **Материализация вместо пиннинга определений:** вставка узла копирует состав в расчёт; определения меняются свободно и влияют только на новые вставки. Трассируемость цены — фиксацией применённых цен/ставок/коэффициентов в строках + `priceListVersion` + `PriceHistory`; версия `NodeDef` — аудит состава.
3. **Дерево расчёта — JSON-документ** в `Estimate.surveyData`; реляционно только разделяемое: прайс, справочники, каталог, снапшоты, пользователи.
4. **Формулы — код** (реестр именованных функций), не DSL. Новые линейки продукции/виды работ добавляются как записи каталога поверх существующих формул — без релиза; принципиально новые формулы — через релиз.
5. **Классы → три флага:** `hasOperations`, `purchasable`, `lockedComposition`.
6. **Домены — тег** узла каталога для группировки в UI, без логики.

> **Как читать ссылки «Библиотека §6.N» из кода.** Нумерация в §6 двойная, и обозначение `§6.2` занято дважды: как **пункт 2 списка выше** (материализация — `template-kns.ts:12`, `:197`) и как **подраздел ниже** (редактор каталога и роль TECHNOLOG — `backend/src/routes/templates.routes.ts:11`, `backend/prisma/schema.prisma:15`). Ссылки `§6.3` (`backend/prisma/schema.prisma:77`, `template-kns.ts:83`, `backend/src/utils/estimate-tree.ts:5`) и `§6.4` (`formulas.ts:4`) — это пункты **3** и **4** списка, подразделов с такими номерами нет.

### 6.2 Редактор каталога и роль TECHNOLOG

Для построения новых типовых расчётов нужен **редактор типовых компонентов и шаблонов** (фаза 3):

- создание/редактирование `NodeDef`: параметры, состав строк (категория, наименование-генератор, ЕИ, выбор формулы из реестра, k_ФОТ), варианты, правила сборки, теги;
- сборка шаблонов изделий из узлов каталога, биндинги параметров на поля ОЛ;
- предпросмотр: материализация узла с тестовыми параметрами и текущим прайсом;
- версионирование каталога (инкремент + запись в AuditLog), публикация «черновик → активен».

Границы, удерживающие сложность: редактор работает **только с данными каталога** — формулы остаются кодом; изменения каталога не затрагивают существующие расчёты (материализация); доступ — новая роль.

**Роль `TECHNOLOG`** (технолог/методолог): CRUD каталога компонентов и шаблонов, чтение прайса; без доступа к чужим проектам и администрированию. ADMIN наследует права. Стоимость введения роли минимальна — RBAC уже есть.

**Что из этого сделано (этап 1).** Роль `TECHNOLOG` есть в схеме и в RBAC (`backend/prisma/schema.prisma:15`), экран — `ntt-calculator/src/views/TemplatesView.vue`, API — `backend/src/routes/templates.routes.ts` (доступ ADMIN + TECHNOLOG, `:23`). Редактируются не `NodeDef`, а **данные**, из которых материализуются шаблоны: нормы патрубков (ключ DN), веса труб GRP (ключ DN+PN+SN) и инженерные матрицы (корпус, эллиптические днища) — upsert по естественному ключу справочника, каждая правка пишется в `AuditLog` (`template.nozzle_norm.upsert` и соседние события, `backend/src/utils/audit.ts:30`). Правка немедленно влияет на новые материализации и не трогает уже посчитанные деревья. Не сделано: редактирование состава узлов и сборка шаблонов из каталога, биндинги на поля ОЛ, предпросмотр материализации, публикация «черновик → активен».
